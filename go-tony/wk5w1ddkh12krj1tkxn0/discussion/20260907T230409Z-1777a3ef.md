CORRECTIONS to the reference data above, both mine.

1. "The store has since been wiped" was not true when I wrote it. It had not been wiped and
   still has not; docd is up on the same volume. Everything else in that comment was measured
   on the store as described.

2. THE THIRD ACCEPTANCE CASE WAS WRONG, AND BACKWARDS. I offered the root read as a demanding
   case. It is the cheapest read in the store, and the reason is a number I did not have then.

THE DOCUMENT IS 3.24 MB.

    snapshot body           3,400,584 B     3.24 MB
    logA + logB         2,323,100,464 B     683x the document
    index resident      1,202,590,842 B     354x the document
    last root snapshot    commit 537,384    1,386 commits behind head

Read from the header records the root snapshot segments point at -- 97 bytes each, carrying
Commit, ScopeOverlay, SnapPos and Timestamp, written after the body they describe, so the
body is the span from SnapPos to the header. Four consecutive snapshots give 3,392,290 /
3,393,285 / 3,400,584 / 3,400,584 bytes, monotone in commit; the Commit field of the last
decodes to 537,384, which is independently what the index says it is.

THE BOUND, REPLACING THE THIRD CASE. A read at a path requires

    the size of the resulting read
  + the largest single log record it must buffer
  + stack

and nothing else. If an intermediate applied state since the last snapshot is larger than the
final answer, that intermediate is itself a result size and is what the bound is stated
against -- it is still a materialized answer, never a count of how much has happened under
the path. So there is no term here for segments beneath the path, for depth, or for history.

MEASURED AGAINST THAT BOUND, both large terms of the read caught in flight are outside it:

    166 MB   index.LookupSubtree(kp, from, to, scope) []LogSegment
             -- returned before a single log entry is read
    511 MB   storage.patchNodesFromSegments([]LogSegment) ([]*ir.Node, error)
             -- every patch in range decoded and held at once

against a document of 3.24 MB. The base side of the same function is already within the
bound: findSubtreeBaseReader gives a reader and applyPatchesToBase folds onto it, streamed.
It is the patch side that materializes, and it materializes because both signatures are
slices whose length grows with the number of segments in range. A slice cannot express this
bound; a cursor can. That is property 1 landing on a signature rather than on a caller, which
is what the proposal says about it.

I have that read's stack and heap profile but not its kpath, and I did not establish what
made its commit range large -- the sizes above are measured, the mechanism behind them is not.

The first two acceptance cases stand as written.
