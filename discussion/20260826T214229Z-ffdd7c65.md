Settled further: the copy is DETACHED, and detached is where the walk stops.

    !get-path      the answer is a root: Parent nil.
    !get-paths     ir.FromSlice(clones) -- the list is a root, each value is parented to
                   the list.

There is no reason to invite a walk up past what was asked for: navigating down is what the
path already did, and the answer is a value, not a second name for a place.

That gives a property worth stating rather than discovering: `(root)` inside a value which
came from a lookup resolves to THAT VALUE, since Root() stops at the detached copy. A
nested lookup cannot climb back out into the document, and the anchor means the same thing
-- "the top of the tree you are in" -- in both places.

The shape already exists in the tree: mergeop.childList (264837c) builds exactly this for
!ir's fields and values, and could be the same helper.

Two mechanical notes for whoever builds it:

  - CloneTo copies Parent, ParentIndex AND ParentField, so all three want clearing on the
    singular answer, not just Parent.

  - ir.FromSlice sets Parent and ParentIndex on what it is handed and does NOT clear
    ParentField. So a clone taken from an object keeps the field name it had there while
    being element i of a list, and !field reads ParentField (field.go) -- so `!get-paths
    a.b[*]` followed by `!all.field X` would answer with names from where the values came
    from, where a native array element answers "". Decide whether the list clears it.
    Not a regression from anything: !ir's list has the same property today, and had it
    before 264837c too, when it held the document's own children.
