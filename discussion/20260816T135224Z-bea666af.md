Wider than filed: the marker is not the only label that masks the op. PARSING puts one there.

`!delete {by: scott}` reads as `!bracket.delete`, so `patchArrayByIndex` saw `!bracket` and fell
to the positional-patch branch. A delete or an insert of anything but a SCALAR was therefore
already broken in the format, with no logd involved:

```
{v: !arraydiff {0: !delete {by: scott}}} on {v: [{by: scott}, {by: dee}]}
  -> cannot patch, unexpected value at $.v[0]
```

So the fix is in mergeop, not in logd: the op is the first label of the chain the registry
KNOWS, found the way SplitChild finds it, and the labels ahead of the op are put back on the
value -- which is what lets a delete compare a braced object against the braced element it is
deleting.

logd still had a part to play. Its marker is metadata about routing, not a label of the value,
so once mergeop restores the leading labels the marker came back as part of the DATA. It now
goes at the tail of the chain (tx.MarkPatchRoot); every reader of it asks TagHas, which scans
the whole chain, so nothing else changes.
