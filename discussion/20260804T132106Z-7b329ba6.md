# The cost is a full document materialization per conditional write

Read from source at 4e41c35, not measured — the numbers quoted below are the
repo's own, from a place where this was already diagnosed and fixed.

## What the two paths do differently

`doCommit` (`storage/tx/coord.go:309`) is one code path for both. The only fork
is `evaluateMatches` at `:336`, and `evaluateMatches`
(`storage/tx/match.go:15-22`) is:

```go
for _, patcher := range state.PatcherData {
        m := patcher.API.Match
        if m == nil || m.Data == nil {
                continue                       // <- unconditional stops here
        }
        doc, err := readState(kpath, commit, scopeID)   // <- conditional pays this
```

`readState` is `Storage.ReadStateAt` (`storage/storage.go:191`), which is
`findSnapshotBaseReader` + read that snapshot + `LookupRange("")` + apply every
patch since it.  So a conditional write materializes the whole document before
it can commit, and an unconditional one never reads state at all.

That is the 60–500x, and it accounts for all three of the observations:

- **The unconditional path is flat** because it does no read.
- **The anchor barely matters** because `ReadStateAt` does not narrow by path,
  deliberately and in its own words (`storage.go:184`): *"kp does NOT narrow the
  result: log entries are whole-document patches, so what comes back is the
  document, root-rooted — a SUPERSET of kp's subtree."*  A match at the entity's
  path and a match at the root read exactly the same bytes.  `kp` is kept in the
  signature as *"the natural hook for a future path-scoped read"* and is
  otherwise unused, because using it to pick the snapshot base broke two
  different ways (issue bvm163tyh12krwcqcsn0).
- **The erratic, non-monotonic profile** is the cost being
  O(patches since the last snapshot), not O(document size).  Snapshots are
  threshold-triggered — `maybeCompact` (`server/server.go:101`) switches on
  `MaxCommits`/`MaxBytes` and resets `commitsSinceSnapshot` — so replay length
  is a sawtooth, and each conditional write appends a commit that lengthens the
  next one until a snapshot resets it.  Where a 150-write run lands on that
  sawtooth is why 500 entities beat 1000: the run is not measuring document
  size.

So it is computing, not waiting — but under `commitMu`, which `doCommit` holds
across eval→write, so it is also the whole commit path's critical section.

## This is the same bug the watch path already had

`server/session.go:749-752`, on why a baseline watcher steps a kept document
instead of re-reading:

> It replaces a full ReadStateAt per event per watcher, which was O(patches
> since the last snapshot): **1.6ms at 50 commits, 62ms at 1550**, paid again by
> every watcher on every commit that reached it.

Those are this issue's numbers.  1.6ms→62ms over that range is the shape of
40ms/58ms/65ms/75ms/270ms/337ms, and "O(patches since the last snapshot)" is the
sawtooth.  The watch path fixed it by keeping `curDoc` and stepping it —
`curDoc = Patch(curDoc, committedPatch)` — rather than restarting from a
snapshot each time, noting *"nothing is kept that was not already built — the old
code materialized a whole document per event and threw it away."*  The CAS path
still materializes and throws away.

## The two questions the issue left open, from source

**Match evaluation or the commit path?**  Match evaluation, and specifically the
`readState` call inside it.  Everything after `evaluateMatches` in `doCommit` is
identical for both arms.

**Does a failing precondition cost the same as a holding one?**  Yes, and very
slightly less.  `readState` runs before `tony.Match`, so the read is paid either
way; a failure then takes the `!matched` return at `coord.go:349` and skips the
write.  Same order, same sawtooth.

## Fix direction

The watch path's remedy transfers, and `commitMu` is what makes it safe: it is
already held across eval→write, so a single stepped head document mutated under
it cannot be torn or raced, and the serialization the CAS fix (b23fdee) needed is
the same serialization a stepped document needs.

- Keep a materialized head document in `Storage`, stepped by each commit inside
  `commitMu`, and have `evaluateMatches` read from it instead of calling
  `ReadStateAt`.  Nothing new is built: `WriteAndIndex` already has the merged
  patch in hand.
- The scoped case cannot step, for the reason scoped watchers cannot
  (`session.go:754-757`): a scope's writes apply last and shadow baseline, so
  folding a baseline patch into a materialized scoped doc lets baseline
  overwrite a leaf the scope owns.  Scoped CAS would keep recomputing until the
  scope layer gets the same treatment — worth confirming which of the two the
  repro exercises, since `ReadStateAt` forks on `scopeID != nil` at
  `storage.go:192`.
- A path-scoped read is the other direction and would help both, but it is the
  thing `storage.go:184` says was tried and reverted, so it is the larger piece.

Not yet verified by running the attached repro; the above is a source reading.
Worth confirming with a profile before building anything, since the prediction is
specific: per-op cost should track commits-since-snapshot, and forcing a snapshot
mid-run should drop it discontinuously.
