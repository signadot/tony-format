Checked 2026-09-13 against go-tony main (05f06090) and verse entity/logdstore.go.

The premise needs one correction: verse uses libctl, and libctl already sends an unwatch by the request id when a Watch's context expires (unwatchAbandoned, watch.go:231) -- the id is the client's own, so the client can and does name it. That path is best-effort with a 5s budget and logs its failure at Debug, so under a burst where every request times out it can fail without a trace; but it is not the leak.

Two verified leaks, both below verse, reproduced with a throwaway libctl test against a real logd:

1. logd server: an unwatch removes the watcher from the hub but nothing ends its stream goroutine. handleUnwatch (session_watch.go:616) and cleanupWatches call hub.Unwatch, which only deletes from the hub's map (watch.go:108); nothing closes the watcher's Events or Failed channel, so forwardEvents/live (session_watch.go:547) blocks on Events until the session's done. Every clean Close on a long-lived session leaves one (*watchStream).live goroutine: after one Watch+Close, hub watchers=0, live goroutines=1. Verse's Since opens and closes a watch per call, and every heal re-establish closes the old one, so this alone accounts for the 9,221 goroutines. These are out of the hub, so they cost no fan-out.

2. libctl -> logd: a watch that fails as a slow consumer is never unwatched on the server. deliver (watch.go:304) closes the watch locally when the buffer is full; verse sees the closed channel and calls Close, as it should; Close (watch.go:269) returns early once closed and never sends the unwatch. After a slow-consumer failure + Close: hub watchers=1, live goroutines=2. That stream stays in the hub, receives every commit and re-reads per event -- the 19-20 cores. A burst is exactly what makes verse's per-event apply+emitDiff fall behind, so each burst fails watches this way, leaks a live stream each, and verse re-establishes; 45 open on the client, thousands on the server. This is 4ynqp7wq item 10.

So verse is ending its watches correctly at its layer; the calls it makes do not reach the server.

Fixes, both small: (a) libctl Close sends the unwatch whether or not the watch already failed locally (or deliver sends it on failure), and the abandoned-unwatch failure logs at Warn; (b) logd handleUnwatch and cleanupWatches end the stream (a done channel on the Watcher closed under the hub lock, which live selects on). Neither of the issue's two proposals is needed for this incident: the connection WAS consuming, so an idle-consumption bound would not have fired, and cancel-by-request-id already exists as unwatch with watchId.
