Clearer, since my notation was cryptic — the three columns are: the field NAME handed to the producer, the tag text TagCompose emits, and what TagArgs reads back from that text.

    name "id"         TagCompose -> "!key(id)"          TagArgs -> args ["id"]        ok
    name "has,comma"  TagCompose -> "!key(has,comma)"   TagArgs -> args ["has" "comma"]
    name "has)close"  TagCompose -> "!key(has)close)"   TagArgs -> args ["has"]
    name ""           TagCompose -> "!key()"            TagArgs -> args []
    name "has.dot"    TagCompose -> "!key(has.dot)"     TagArgs -> args ["has.dot"]   ok
    name "*"          TagCompose -> "!key(*)"           TagArgs -> args ["*"]         ok

You are right that no such tag exists in a document, and that is the point rather than a counter-example: the grammar has no way to write those names, so TagCompose emits text which is not the tag it was asked for, and TagArgs then reads the text as written. Nothing is wrong with the parser.

So the defect, if it is one, is the producer accepting a name it cannot render — scope_overlay handing a field name to TagCompose without checking it fits. The narrow fix is to refuse, not to extend the grammar.
