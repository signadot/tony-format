Half fixed in c3811ef, and the diagnosis in the original report was incomplete.

FIXED: the empty-base branch of the streaming processor folded each patch into an accumulating result and stripped the marker only after the last fold, so every patch after the first was applied to a document still wearing the previous patch's marker. That is the route the four-op reduction takes. Regression test: TestAPatchRootMarkerDoesNotReachTheDocument.

NOT FIXED: at LOGD_SEEDS=500 LOGD_LOWERING=all the claim differential goes from 2 broken to 1. The survivor (seed 272) arrives by another route and looks different -- the document being patched already has markers nested at several depths, some of them DOUBLED:

    a: !logd-patch-root.logd-patch-root { b: !logd-patch-root.logd-patch-root {} ... }

Two things ruled out while chasing it, recorded so nobody re-runs them:

- MarkPatchRoot composing onto an already-marked node is NOT the problem. It does produce the doubled tag, but StripPatchRootTag clears both labels -- ir.tagFilter drops every matching label, not just the first. An idempotence guard there changes nothing observable and was reverted.
- Making the snapshot path's strip recursive (StripPatchRootTag -> StripPatchRootTagRecursive at processor.go's emit point) also changes nothing on this seed. Reverted.

So the doubled markers are arriving with the patches, from a producer that has not been found, rather than being introduced or retained at either emit point.
