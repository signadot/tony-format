## Compat note: the other direction — tony documents read *by* YAML parsers

Everything above is about reading YAML into tony. This is the reverse question,
which came up while fixing pkj422gkh12kr24gj1n0 (tag names absorbing `,`, `}`,
`]`). Measured against PyYAML 6, gopkg.in/yaml.v3 v3.0.1 and goccy/go-yaml
v1.15.13, on the spellings a tag-plus-null produces.

### The normal form is clean

What the encoder writes parses in all three, identically:

```
{
  a: !delete null
}
```

PyYAML keeps key `a`, tag `!delete`, value `null`. yaml.v3 and goccy both
decode into `any` without error (the unknown tag leaves the scalar a string,
which is the right thing for a consumer that does not know tony's operators).
So `o view` output is YAML-readable, and this note is only about documents
written by hand.

### Hand-written abbreviations diverge, and it is not a parser bug

| written | PyYAML | yaml.v3 | goccy |
| --- | --- | --- | --- |
| `{a: !delete null}` | ok | ok | ok |
| `{a: !delete }` | `a` → tagged null | `a` → null | **error** |
| `{a: !delete , b: 1}` | ok | ok | **error** |
| `{a: !delete}` | **error** | **error** | **error** |
| `{a !delete}` (key set) | key `"a !delete"` | same | same |

Three things fall out of that, in decreasing order of how much they matter:

1. **The key-set sugar is unreadable as YAML, inherently.** `{a !delete}` is
   one plain scalar key `"a !delete"` in every implementation, and no
   implementation can do otherwise: `!` is a tag indicator only at the start of
   a node, and a plain scalar runs greedily through an interior space. There is
   no node boundary before `!delete` without a `:`. This is a property of
   tony's key-set-with-tag sugar, not a bug anywhere — a YAML parser reading
   hand-written tony of this shape gets a wrong answer silently, with no error.

2. **A tag shorthand needs whitespace to terminate.** `{a: !delete}` fails in
   all three (PyYAML: "while scanning a tag") because `}` does not end a tag
   shorthand. Tony accepts it since pkj422gkh12kr24gj1n0. So the one-entry flow
   mapping is YAML-readable only when written `{a: !delete }` with the space —
   and then only in two of the three parsers, per (3).

3. **goccy diverges on tags at implicit nulls.** `{a: !delete }` and
   `{a: !delete , b: 1}` are accepted by PyYAML and yaml.v3 and rejected by
   goccy with `could not find '{' character corresponding to '}'`. A tag on an
   implicit null in flow context is legal YAML — nothing in the implicit-null
   production excludes properties — so this looks like a goccy defect rather
   than a difference of interpretation. Not filed upstream.

Note that tony itself refuses the *block* form of the same thing: `a: !delete`
alone on a line is a dangling colon, and the parser asks for `null` explicitly.
YAML accepts it (all three, as a tagged implicit null). So on tags-at-nulls
tony is stricter than YAML in block context and looser in flow context.

### What this does not ask for

No code change is implied. The tokenizer fix stands, the encoder already emits
the portable spelling, and (1) is not fixable without giving up the key-set
sugar. What it argues for is a line in the interop section of the docs saying
which hand-written spellings survive a YAML parser, since the answer is not
guessable and the failure in case (1) is silent.
