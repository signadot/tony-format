## Space as the delimiter, and a correction to the analysis above

The section \"there is no free character\" measured what the PARSER accepts. The
printer is the other half, and it does not agree.

`token.KPathQuoteField` is `NeedsQuote(v) || strings.ContainsAny(v, \".[{\")`, and
NeedsQuote quotes anything containing a space. Measured, one field per row:

    \" \"  field \"a b\"   prints as  \"\\\"a b\\\"\"   QUOTED
    \",\"  field \"a,b\"   prints as  \"\\\"a,b\\\"\"   QUOTED
    \"\\t\" field \"a\\tb\"  prints as  \"\\\"a\\\\tb\\\"\"  QUOTED
    \"/\"  field \"a/b\"   prints as  \"a/b\"       bare
    \"|\"  field \"a|b\"   prints as  \"a|b\"       bare
    \":\"  field \"a:b\"   prints as  \"a:b\"       bare
    \"@\" \"~\" \"-\" \"+\"                            bare

So for PRINTED paths, space is free. No kpath this system emits ever contains an
unquoted space, which means a Delim(' ') reader cannot misread a path taken from
a log line, an error message, an index key, a snapshot, or the wire. '/' fails
exactly there: \"a/b\" prints bare today, so a slash reading silently re-splits
stored paths -- the gx8xvgmph12krbjpg1n0 shape, which is the risk this proposal
was written to avoid.

The \"no free character\" finding is still true for hand-typed input. It is not
true for canonical output, and space is the only candidate where those two
diverge in the safe direction.

## What space would cost

1. THE SHELL, which is the motivation. A kpath is one argv word -- `o get
   <objectpath> [files]`, path first, files after -- so `o get users example.com
   tls doc.tony` cannot be parsed: nothing separates segments from files. It has
   to be `o get \"users example.com tls\" doc.tony`, trading quote-when-a-field-
   has-a-dot for quote-always. That is a loss on short paths, which are most of
   them.

   The form that pays off is to stop making it a string. The shell already splits
   on spaces, so let it do the parse: `-k users -k example.com -k tls`, or a
   terminator (`o get doc.tony -- users example.com tls`). No delimiter option,
   no quoting rule, no escaping. That is proposal 3 above, and it is what \"space
   delimiter\" is actually reaching for.

2. INVISIBLE AND NOT IDEMPOTENT. \"a  b\": collapse, or an empty segment? Collapsing
   makes the parse non-injective, so a path with an empty field name cannot be
   spelled. Not collapsing turns an invisible typo into a different path. Leading
   and trailing space is the same fork -- Parse(\"a \") is a field named \"a \"
   today. Runs of spaces are mangled by copy-paste, YAML folding, HTML and
   spreadsheets. '.' is visible and survives all of them.

3. IT NEEDS A RULE FOR THE BRACKET FORMS. \"a [0]\" is the field \"a \" then an index
   today. Under a space delimiter, is that space a separator (an empty segment?)
   or adjacency? '.' needs no such rule: \"a.[0]\" and \"a[0]\" are already distinct.

4. AMBIGUITY WHEREVER A PATH IS EMBEDDED IN TEXT. \"no such path: a b c\" reads as
   three things; %20 in URLs; and a space-delimited path cannot be
   double-click-selected in a terminal.

5. IT RELOCATES QUOTING RATHER THAN REMOVING IT. With Delim(' '), a field
   containing a space needs quoting. For the shapes that motivated this issue
   (example.com, 1.2.3) that is a win; for human labels (\"first name\", display
   titles) it is a loss. Per data shape, as section 1 already says.

## Conclusion

Space is the safest value to SUPPORT as a Delim: it is the only candidate that
cannot misread the system's own output, and it suits domain- and version-shaped
data. It is dominated for the CLI, which is where the pain actually is; there the
answer is segments as argv, not a different separator inside one word.
