Decided (Scott): the operation is nested, `scratch: {write: {path, data}}` / `scratch: {read: {path}}`, as `schema: {get, set}`; a write echoes its data as a patch does; writes are coalesced behind a flush tick (`storage: {scratchFlush: 1s}`, zero = default), order kept. Scratch is assumed large and busy.

Second draft of the plan (commit 3d79aa5d on `issue-r482sz5rh12ksj`), after a review against the code. What the review changed:

- The mutex is held across apply. As first sketched, two sessions writing at once could each patch the same document and one write vanish.
- A write patches in place (`PatchOwned`). `Patch` clones the whole document per call, so "a write is O(spine + data)" was false under it. The flusher copies the document under the mutex once per tick and encodes outside.
- `Patch` and `GetKPath` panic on a nil document; the plan now bases an empty scratch on `ir.Null()` for writes and answers absent for reads, and a scratch deleted to nothing flushes as an empty file.
- Unsafe mergeops (`!pipe` and kin) are refused with `invalid_diff`, as the document refuses them. Plain `Patch` would have run them.
- Config does not reach `storage.Open`; a `SetScratchFlush` setter in `server.New` does, beside `SetDurability`. Durability is read at each flush.
- Zero in config means the default everywhere, so there is no write-through mode; tests flush through `Close` or the package's `flushNow`.
- The flusher is a ticker, so a failed flush is retried; the first sketch was nudge-driven and a failure with no further write would never retry.
- Comments are kept through patch, encode and parse, as the store keeps them.
- Absent on the wire is an omitted `data`, never `data: null`, per the presence rule in `api/state.go`.
