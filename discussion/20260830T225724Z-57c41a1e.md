Two corrections to this issue's framing, then a candidate that would make most of it moot.

## "The state" is Storage.head, and the store is already (path, commit)-addressed

Earlier text here talked about the state becoming "a path-addressed store" as though that
were a future architectural change. It is not: log segments, snapshots and the index are
already addressed by (path, commit). The only thing that is a materialized tree is
`Storage.head` -- the whole baseline document at the last commit (head.go:238) -- plus the
per-scope heads from installScopeHead and each watcher's stepped document.

Two properties of it that were being talked past:

  - it is a CACHE WITH A FALLBACK. steppedBaselineAt returns s.head only when
    headCommit == commit, and otherwise replays, counting the miss ("a stream of them is a
    store paying a full read per write"). So bounding it is a cache policy over an existing
    fallback, not a correctness change -- the same shape as bounding the index
    (qvn7ptxch12krxzt9hmg).
  - it is STRUCTURALLY SHARED: "untouched subtrees are shared with earlier heads and with
    any watcher document stepped from the same patches" (head.go:41). So rkb7p8v5's "every
    watcher folds the whole document" is a statement about TIME. Restating it as memory --
    which this issue did -- is wrong: a watcher's incremental residency is the path it
    stepped, not a document.

Residency for a keyed array of N is therefore roughly one set of element nodes, shared
across head and watchers, plus the index's node per path segment. Not a copy per watcher,
per scope or per commit.

## Candidate: store a !logd-key array AS AN OBJECT

Rather than teaching three layers to address `items("G")`, make it `items.G` -- a keyed
collection is stored as an object keyed by the key value, positional addressing does not
apply to it, and it is then not a special case anywhere.

What that dissolves, rather than reorders:

  - the snapshot fence, entirely. stream.State.CurrentPath already emits field paths, with
    no schema and no format change to the builder. The one item in this plan that needed a
    format change needs none.
  - the projection fence: an object patch has no !key operator to descend.
  - the re-rooting fence: a field re-roots.
  - keyedListOp itself: identity merge becomes objMergeFast, which already shares.

And it composes with bounding head and index instead of competing: one fanout mechanism to
bound, for objects and keyed collections alike.

What it has to answer, and these are the real cost:

  - DUPLICATE KEYS are reachable today. TestKey_ReplaceWithDuplicateKeys shows a plain
    positional write over a keyed array merging positionally, so `[{name: a}, {name: a}]`
    can be stored. As an object that state has no representation, so this forces a decision
    the system currently leaves open.
  - AN ELEMENT WITHOUT THE KEY FIELD has no name. keyedListOp deliberately keeps such an
    element ("no patch element can address it, so it is simply not one of the ones being
    merged"); as a field it cannot exist.
  - ORDER. Objects sort, and objMergeFast requires sorted fields. A collection written as
    an array comes back in key order. For an identity-keyed collection that is arguably
    right, and it is still a visible change.
  - WHAT THE CLIENT SEES is the decision the rest hangs off. Internal-representation-only
    means translating values AND paths at the boundary, and two vocabularies for one thing
    is what drifts (see DeliverablePatch). Saying a keyed collection IS an object is
    cleaner inside and is a format decision.
  - NON-STRING KEYS: ElemKey admits strings, bools and numbers; the mapping to a field name
    has to be stated and reversible.
  - POSITIONAL OPERATIONS on such a collection (!arraydiff, !insert) have to be REFUSED at
    the write rather than silently meaning something else.

Worth saying plainly: this is the first framing here where the work gets smaller instead of
being resequenced. Every previous version of this plan kept the same fences and argued
about their order.
