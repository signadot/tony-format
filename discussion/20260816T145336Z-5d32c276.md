Narrow half done in ee1b9d4: the officially unsafe operations are restricted, using the
mechanism that was already there.

mergeop.Unsafe and the RejectUnsafe PatchOpt predate logd storing anything, and nothing ever
set the option -- an early-development gap rather than a decision. api.NextState sets it now,
which covers every one of the eleven places logd applies a patch, and NewPatcher refuses a
write holding such an operation so a store never has to fail reads to enforce it. The refusal
is invalid_diff. mergeop.FindUnsafe asks of a whole patch what Unsafe asks of one tag, and
stops at !raw so an escaped document that CONTAINS a patch is still storable.

Still open here, and it is the half with teeth: a client-supplied !arraydiff or !strdiff in the
patch BODY commits and then no read of the store succeeds again. That is permanent, and it is
not about execution. Holding a write to the whole storage vocabulary would close it, and still
has to settle what to do about the !arraydiff MergePatches manufactures for every positional
write -- validate the client's data before merging, or state the baseline subset.
