# status report

## the !key change in ir + index (working tree on 265cbc8, not yet committed)

Two defects found while adding an `!at(kpath)` matchop, both sitting on the path this
issue's approach depends on.

1. **ir kpath navigation never resolved a `(key)` segment.** `getKPath` fell through
   its index/field branches to `return res.Clone()`, so `items("W")` yielded the whole
   ARRAY, and any further segment errored ("unexpected next segment without index or
   field"); `listKPath` likewise appended the container. Fixed in `ir/kpath.go`: a
   `(key)` segment resolves against the array's `!key(field)` tag. `Node.KeyField()`
   and `ir.ElemKey()` are the shared reading of "what keys this element" — `GetKPath`
   takes the first match, `ListKPath` all of them (a list may hold one key twice).

2. **`index/log_segment.go` read the key field with `ir.TagGet(n.Tag, "key")`, which
   never matches** — `TagArgs` returns the head WITH its `!` ("!key"), so the tag
   fallback was dead code and only the schema (AutoIDFields) route ever produced keyed
   index paths. `build.go`'s stated contract — "Schema is nil here - we rely on !key
   tags stored in the patches" — therefore did not hold: a rebuilt index had positional
   paths for keyed arrays while a live index under a schema had keyed ones. Same log,
   two index shapes. The key field now comes from `n.KeyField()` and the value from
   `ir.ElemKey`, which also handles a nested key field (`!key(meta.name)`) and
   non-string keys.

Remaining gap, unfixed: **the schema route still writes index paths its own patch
cannot resolve.** `tx/auto_id.go` injects the id FIELD into each element but no
`!key(id)` tag, so the index records `items("<id>")` while
`entry.Patch.GetKPath("items(\"<id>\")")` finds nothing. Before (1) that call returned
the whole array — wrong subtree folded in; now it returns nothing — contribution
dropped. Live site is `internal/patches/processor.go` `subtreeAt`.
hbn7ptxch12krs778smg closed with exactly this question open: "Should we auto-inject
!key tags based on schema or reject patches without?"

Also removed `storage.readPatchesAt` and its `patchAtSegment` type (uncalled).

## testing status of !key in logd

Behavioural coverage is one test at one layer: `TestScope_COW_KeyDurability` (a scope
adds a key while baseline adds others). `index/schema_test.go` covers index path SHAPE
only — the schema route pre-existing, the tag route added with the fix above.
`testdata/orders.tony` and `auto-id.tony` carry `!key` but no Go test reads them; the
testdata README documents them as manual `o sys logd session` fixtures.
`tx/auto_id_test.go` and `api/schema_test.go` cover ID injection and schema parsing,
never a keyed merge.

Not covered anywhere:

- identity merge at baseline — patching the SAME key twice (the one keyed test only
  ever adds distinct keys, so the central !key semantic is unguarded)
- a keyed array through snapshot creation/read, and a keyed patch applied ONTO a
  snapshot base
- a keyed array through compaction (`PatchesSurviveCompaction` uses plain scalars)
- index rebuild from a log of keyed patches (the `build.go` contract above)
- `patchMayAffect`'s op-tag fall-through: its doc names !replace/!delete/!key/!arraydiff
  as ops that must force the authoritative recompute, but `patchmayaffect_test.go`
  tests only quoted segments and plain merges, so that branch is untested for every op
  it names — and the watcher's soundness argument rests on it
- multi-participant merge into one keyed list (`tx/merge.go`)
- watch deltas for a keyed change (no `!key` anywhere in the server tests)

Probed the first, second and fourth of those through the real storage API before
writing this, and all three pass today: a same-key update merges without a duplicate, a
keyed patch still merges on a snapshot base, and a close/reopen rebuild reads
identically. They work; they are simply unguarded. One observation from the probe: the
materialized read carries NO `!key` tag on the array, so merging keeps working only
because the PATCH supplies it — this issue's "resolves !key away" property, visible at
the read boundary.

## conclusion

The approach recorded above says the overlay can key by index path because the key is
already IN the path, "keyField from schema or the !key tag in the data". That was
half-true when written: the tag half was dead code, so tag-carrying data got positional
index paths and a rebuild got positional paths for everything. The premise is now real
for tag-carrying patches and still absent for the schema route.

So the logd change needs re-incorporation into a refreshed dev plan before the overlay
is built: settle the auto-inject-vs-reject question inherited from
hbn7ptxch12krs778smg (an overlay keyed by index path is sound only if every keyed
write's own patch is navigable by that path), and land the keyed coverage listed above
as the guard the overlay gets built against.
