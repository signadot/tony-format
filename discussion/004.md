Reproduced this issue's measurement exactly before fixing — the repro here (5 commits to
`demo.x.hot`, switch, 3 more, switch, `Compact` with Cutoff 0) leaves **9 of 31** segments
reachable from `demo.x.hot` unreadable, each failing `read interrupted by compaction`, at
`kp="demo"`, `kp="demo.x"` and `kp="demo.x.hot"` for commits 5, 6 and 7.


Added `Index.AllSegments`: walks the whole tree and returns every segment with its full
path. Deliberately distinct from `LookupRangeAll("")`, which returns the root node's own
commits and descends only along a path it is given — it is given none, which is the whole
bug.

Compaction captures that once, before anything moves, and groups it by entry identity
`(StartCommit, StartTx, ScopeID)` — the fields every copy of one entry shares, since
`indexPatchRec` passes the same entry, file and position down every level of the recursion.
`updateIndexPositions` then repositions every copy of a moved entry and `removeFromIndex`
removes every copy of a dropped one, instead of just the root.

Survivor selection is untouched and still runs off the root, which is the authoritative
entry set (every entry has a root copy). Only the two maintenance passes changed.

One snapshot of the map serves both passes: `updateIndexPositions` only touches survivors,
so the non-survivors `removeFromIndex` looks up are still where the map says they are.


Comment 003 was right that a Cutoff-0 test only exercises the first mechanism: with Cutoff 0
every baseline patch is dropped and only snapshots survive, and snapshots are indexed at the
root only, so nothing is left to reposition. The scope-patch construction it suggested gives
the second directly, and it is now a test. Without the fix it reproduces comment 003's
measurement to the byte:

All three tests are regressions, not probes, and each was confirmed to fail at `5e67b35`

Note on the fix approach: comment 003 suggested maintaining the below-root copies from the
entry's own patch node, re-running indexPatchRec's traversal, rather than walking the index.
I went with the index walk because it does not require re-reading and re-parsing each entry
during compaction, and because it is robust if the indexed paths ever diverge from what a
fresh traversal would produce. If entry counts get large enough that the walk shows up, the
traversal approach remains available.
