Comment #001 said `bsEscQuoted` and `QuotedToString` were two hand-maintained implementations of
the same escape grammar and that any divergence between them was a crash. **That was wrong**, and
it pointed at the wrong fix. Fuzzing found no divergence at all: 9.7M executions of "scanner
accepts *d* → decoder must not panic on `d[:n]`", zero failures. On the byte range `bsEscQuoted`
actually returns, `QuotedToString` was already safe.

The real divergence is between the token package and three callers that reimplemented it.


`token.Unquote` is the correct operation and it already existed:

```go
func Unquote(v string) (string, error) {
	b := []byte(v)
	n, err := bsEscQuoted(b)
	if err != nil { return "", err }
	if n != len(v) { return "", ErrUnterminated }
	return string(b), nil        // <- validated, then never decoded
}
```

Its validation is exactly right — the `n != len(v)` check is what rejects `"a"b"`, the case that
needs no invalid escape at all (the scanner accepts it, but only as its first three bytes, and the
caller then hands the decoder all five). But it returns `string(b)`: the input verbatim, quotes and
escapes intact. `Unquote("\"a\\nb\"")` returned `"a\nb"` with the quotes and a literal backslash-n.

So the one correct API did half its job, was therefore useless, and had **zero callers**. The three
places that needed it each hand-rolled a shape test instead:

```go
if len(s) >= 2 && (s[0] == '"' || s[0] == '\'') && s[len(s)-1] == s[0] {
	return token.QuotedToString([]byte(s))
}
```

That guard admits anything shaped like a quoted string and drops the validation that made the
original correct — so arbitrary stored field keys reached a decoder that panicked on malformed
input. The library's bug and the callers' bug are the same bug seen from two ends.

Worse, the broken behavior was **pinned by a test**. `TestQuoted` asserted `uq != q` — that
"unquoting" returns the *quoted* form unchanged. That is why it survived.


Confirmed reachable, all through the shape guard:

| stored field key | scanner verdict | old result |
|---|---|---|
| `"a"b"` | accepts (3 of 5 bytes) | panic `internal string: trailing` (`quoted.go:207`) |
| `` "\`" `` | bad escape | panic `slice bounds out of range [:13] cap 4` |
| `"a\qb"` | bad escape | panic `slice bounds out of range [:14] cap 6` |
| `"\—"` | bad escape | panic `slice bounds out of range [:15] cap 6` |

The `:247` panic never actually fired as written — every invalid-escape case died first inside its
own panic *message*, `d[i-sz-4 : i+10]`, which runs out of bounds on short input. The intended
diagnostic has probably never been printed. That is why the original panic text was unhelpful.


- `Unquote` now decodes: it validates with `bsEscQuoted`, requires `n == len(v)`, additionally
  requires the value to open with a quote (so a bare key like `aba` is not "closed" at its final
  `a` and decoded to `b`), and only then calls the decoder. Panic-free by construction — that
  composition is precisely the invariant the 9.7M-execution fuzz confirmed.
- `QuotedToString` no longer panics. The core is now `quotedToString(d) (string, error)`;
  `QuotedToString` keeps its signature and returns the value decoded so far, so `Token.String` and
  every `fmt` verb that reaches it cannot take down a process over one bad byte. The
  `d[i-sz-4:i+10]` slice is gone.
- Both `unquoteFieldKey` definitions (`logd/server/session.go`, `storage/tx/match.go`; the third
  site, `logd/server/match_data.go:50`, calls the first) now just use `token.Unquote` and fall back
  to the raw key when it errors.
- `TestQuoted` now asserts the real round trip.

Tests: regression cases for all six former panics at the token level and at both `unquoteFieldKey`
sites; `FuzzUnquoteNeverPanics` (6.3M execs) and `FuzzQuoteRoundTrip` clean. Full repo green.


`prfzxpa2h12ks3vscxn0` — a correctly encoded U+FFFD is rejected as `bad utf8`, because the scanners
test `r == utf8.RuneError` without `sz == 1`. Eight sites. Deliberately **not** fixed here;

The session-boundary `recover()`. There is not a single `recover()` in the non-test codebase, and
21 goroutine launch sites in the docd/logd server packages. `startSession` → `go runSession` →
`session.Run` → `readPump` handles error *returns*; a panic unwinds past `defer wg.Done()` and
takes the process, so one client's malformed document kills every session plus any in-flight write.

Worth doing, with one caveat: a bare `recover()` is right for decode panics, whose damage is
confined to one session's data, and wrong as a blanket policy — a panic from a corrupted index or a
violated storage invariant is not confined, and swallowing it keeps the daemon serving state it
should not trust. Recover at the session boundary, log with the stack, fail only that session, and
count it so a recovered panic is loud rather than invisible.
