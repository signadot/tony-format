REFERENCE DATA: a production store measured under memory stress, offered as a workload the
rebuilt API has to clear -- not as a defect list. Three of the four facts below are the shape
this proposal already names, with numbers on them; the fourth is what the shape cost.

Measured on verse staging (docd-0, EKS, 5GiB cgroup cap) on 2026-09-07, from the running
process and from index.gob read off the volume. The store has since been wiped. index.gob is
preserved byte-verified -- 170,374,577 bytes, md5 40739b872159813e8fb68baf69834f1b -- with
five heap profiles spanning three regimes and a 30-sample memory series.

THE STORE

    commits (index MaxCommit)      538,770
    distinct paths                  46,836
    log segments                 4,519,816     96.7 per path
      snapshots (Start==End)           246     0.0%
      patches                    4,519,570     100.0%
      spine                      1,520,318     33.6%
      scoped                         1,865
    logA / logB on disk          1.17 GB / 1.15 GB
    index.gob                      170 MB

1. EVERY SNAPSHOT IS AT THE ROOT. All 246 sit on the root node; each of the other 46,835
   paths has none. So the state of any non-root path is reachable only by replaying that
   path's whole patch history -- verse.git.ref 126,455 patches, verse.github.issue 78,144,
   verse.github.comment 56,786. A cursor over the event store is bounded only if there is
   something bounded to seek TO, which is where property 1 and property 5 meet: what the read
   interface can promise depends on what compaction leaves behind to seek to.

2. THE INDEX GROWS WITH COMMITS x DEPTH, NOT WITH PATHS. The ten largest paths hold 30.1% of
   all segments and every one of them is a shallow ancestor:

       345,572  verse
       345,269  (root)
       153,282  verse.github
       139,804  verse.git
       126,455  verse.git.ref

   Roughly two commits in three leave a segment on the root and on `verse`. 46,836 distinct
   paths carry 4.5M segments. This is qvn7ptxch12krxzt9hmg with a number on it: the bound
   cannot be stated per path.

3. COMPACTION HAS NEVER RUN HERE. dlog.state is "B 0 0 1153317526" -- active B, genA 0,
   genB 0 -- and IncrementGeneration is reached only from compaction.go, so neither file has
   been compacted across 538,770 commits. Property 4 says the substrate kept compaction; this
   store says it was never exercised, so its cost in practice is unmeasured. Collapsing each
   (path, scope) pair to a single snapshot is 4,519,816 -> 47,648 segments, 94.9x. Read that
   as the headroom property 5 is arguing over, not as a proposal.

4. WHAT THE SHAPE COST. The index is 1.12 GB resident, 85% of a 1.31 GB live floor, ~266
   bytes of B-tree leaf per segment. One ReadSubtreeAt held 743 MB in flight -- 511 MB
   materialising patches, 166 MB in LookupSubtree. `o sys up` was OOM-killed against the 5GiB
   cap every ~2.5 minutes; GOMEMLIMIT=3500MiB converted the kill into GC pressure and took
   the lifetime to 2h46m without touching any of the above. A whole-verse read never
   completed at all, at any limit.

THE BAR. A design carrying property 1 should serve a store of this shape with a working set
set by the delta and the path, and with no heap ceiling configured at all. Three cases worth
stating as acceptance:

  - read one field beneath verse.git.ref -- a path carrying 126,455 patches and no snapshot;
  - watch one issue while the sources commit at the rate that produced 538,770 commits;
  - the root read, which under property 1 is a cursor at the root, and which is the read that
    could not complete here at any limit.

If any of those still needs a memory ceiling to survive, the line moved without holding.

CAVEAT ON THE NUMBERS. The scale figures are exact, walked from index.gob with the same
index package the store uses. The 266 bytes/segment is B-tree leaf storage alone -- the
KindedPath strings land elsewhere on the heap -- so it understates the per-segment cost.
