## Answer: no, not in logd and not in docd. pong(C) does not mean the session's watches are current through C.

### logd

A commit gets from the watermark onto the session's stream as a watch event in three asynchronous steps. The pong skips all three:

1. `tick.publish` (storage/tick.go:71) advances the watermark and queues the notification, both under one lock. From that moment `GetCurrentCommit()` reports C.
2. The tick's **dispatcher goroutine** (tick.go:110) later calls `WatchHub.Broadcast` (server/watch.go:145), which does a non-blocking send into each matching watcher's buffered `Events` channel.
3. Each watch's **own goroutine**, `watchStream.live` (server/session_watch.go:630), receives from `Events`, steps (a scoped watch re-reads here), and only then calls `s.send` onto `s.outgoing`.

The ping is handled on the session loop (server/session.go:347). It reads the watermark and puts the pong on `s.outgoing` straight away. Sharing `s.outgoing` gives FIFO order only between items already enqueued. When the ping arrives, the event for C can still be in the tick queue, in `Events`, or partway through a step. So pong(C) can overtake it.

A `match` isn't a barrier either. It runs on its own goroutine (session.go:310) and answers at the commit it read, with nothing ordering it against the watch goroutines. What is ordered is read-your-writes: a plain patch runs on the loop, so a read dispatched after it sees the commit. That's about the store's state, not about what the watches have delivered.

So the `PongResult` doc sentence, "it is not a promise that the client has seen everything below it", is about server-side ordering as well, not only about the client reading asynchronously.

### docd

docd answers the ping itself with `Server.seen` (docd/server/server.go:28, client_session.go:214). That is the highest commit docd has reported to **any client on any session**. It is a lower bound on the head and has no tie to this session's watches. A pong from docd says even less than one from logd.

### Would a barrier be possible?

There's one point to settle before choosing a mechanism: **a watch never hears about a commit that doesn't reach its path.** `Broadcast` filters on `matchesPath` before enqueueing. `accountFor` covers commits the stream received and found didn't reach it, and ones that never arrived don't advance it. So "each watch has accounted for everything up to C" can't be read off the watch's own state. A barrier has to be built from:

- the tick dispatcher being past C, meaning every notification ≤ C is already in its watcher's `Events`; and
- each of the session's watch streams having processed everything in `Events` with a commit ≤ C.

Both are achievable. Some ways to do it:

- **(a) A ping that waits:** wait for the dispatcher to pass C, then put a marker through each of the session's watcher channels and send the pong when every stream has consumed it. That's a real change to the ping. The loop blocks while it waits, and a slow or stuck watch delays the liveness probe, which is the thing the ping is for.
- **(b) A separate request,** e.g. `sync`, with the same mechanism, run off the loop so the ping stays a pure liveness probe.
- **(c) A per-watch progress event:** a watch says "accounted through C" occasionally or on request. verse would then check `C ≥ R` for the perms watch alone, without waiting on the session's other watches. This is the narrowest fit for what verse needs, which is one watch, not the whole session.

Through docd, any of these would have to be forwarded to the mount behind the watched path, not answered from `seen`.

Which of these, if any, is a contract decision for the logd owner. Until one exists, verse's re-read barrier is the correct way to get this guarantee.
