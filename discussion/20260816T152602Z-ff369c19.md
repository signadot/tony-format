Half done in 727faf5: a scope keeps its own document and steps it, so a RUN of scoped writes is
flat.

    unconditional write, cost of the Nth        first     @50      @200      @400
      baseline                                  403µs     357µs    371µs     427µs
      scoped, before                            466µs     1.6ms    7.9ms     22.6ms
      scoped, now                               442µs     389µs    379µs     413µs

It reached further than the write it was for: a scoped CONDITIONAL write with the overlay OFF
was 2.4ms at N=50 and 16.4ms at N=400, and is now ~370µs flat, because the precondition reads
the same kept document (scope_overlay_costs_test.go).

The condition for using it is that the kept document is at exactly C-1, which is self-checking:
commits are numbered globally, so anything else committing leaves this scope's document a
commit behind. Nothing is invalidated by hand.

WHAT IS LEFT is the interleaved case -- a scope writing while baseline writes too. Every
baseline commit leaves the kept document a commit behind, so the next scoped write rebuilds it:

    scoped, baseline interleaved                546µs     3.1ms    21.5ms    71.0ms

That is what a scoped write cost before any of this, not a regression from it, but it is the
shape a real deployment has: baseline traffic does not stop while a sandbox writes.

The answer is a different keeping. Rather than the folded VIEW (baseline+scope), keep the
scope's own overlay -- the delta the scope owns, which is what BuildScopeOverlay computes -- and
step THAT with each scoped write, since the storage vocabulary is absolute and composes:
overlay' = apply(overlay, patch). The scoped view is then apply(baselineHead, overlay), and the
baseline head is already current at every commit. Cost per scoped write becomes O(the scope's
own footprint) rather than O(commits since the last snapshot), and it does not care what
baseline is doing.

That overlaps 5hmq80f3h12krh1mbsn0 (bounded op-preserving scope overlay), which is about
bounding the same object on disk. Worth doing as one piece of work rather than two.
