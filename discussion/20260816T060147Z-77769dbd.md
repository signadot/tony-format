Two measurements to add, from checking this against v0.0.144.

THE CARRIER LEAKS unless it is also marked omit. The example here spells it
`GatesDoc []string ` + "`" + `tony:"-"` + "`" + `, which hides this, but a field-level comment= alone
does not exclude the field it names -- nothing recognises the annotation, so the
named field is an ordinary member:

    Rules        []Rule   `tony:"field=rules,comment=RuleComments"`
    RuleComments []string

encodes to

    RuleComments: []
    rules:
    - name: a

A bogus key in a stored document, and one that decodes back into the carrier. The
struct-level annotations had the same problem and were fixed by excluding the
carriers where the field list is derived (fb23481, 668e74b); whatever honours the
field-level ones has to exclude them the same way, in both modes and on both
paths.

WHAT WORKS TODAY, precisely, so the gap is not overstated. On the charter shape:

    rules:
    # about rule a
    - name: a
    # about rule b
    - name: b

rule b's comment survives a decode and a re-encode, through Rule's own
struct-level comment= (this is new in v0.0.144 -- it used to be discarded by the
parser). Rule a's does not, and cannot: a block array begins at its FIRST element,
so a comment above that element heads the ARRAY, exactly as a comment written
above `rules:` does. Both land on the field's value, which is the thing no
annotation can currently name.

So the visible symptom for a charter is narrower than "list comments are lost":
every rule's comment survives except the first one's, which reads as an off-by-one
rather than as a missing feature.
