Withdrawing one line of mine, and proposing a simpler read rule in its place.

**No loud failure at a declared path.** My 09:42 comment ended with "a path given a short cutoff wants a read past it said … so a rule that does come to read one fails loudly." That guard only matters if something reads a declared path at a past commit, and the rule since is that only paths nothing reads that way get declared. So a loud failure protects against a wrong declaration, and costs every read that *covers* a declared path rather than names it: a listing of `verse.verse.iods` at a past commit, a firing whose read is a subtree holding an iod, a watch replay over the record. Each would have to fail, or partly fail, for one field inside it. That is mixed reads with two kinds of history, which complicates the semantics where failing loudly is meant to simplify them. The store-wide cutoff is unaffected: a read past it is still cpqj2tf6h12kr5jxqxn0.

**A past read at a declared path answers the current value**, in place of "the newest surviving statement at or before that commit". At `0` that rule answers wrongly: the only surviving statement of a leaf (say `out.lastPass`) can be newer than the commit asked for, so nothing survives at or before it, and the read says the field was absent at a commit where it stood. The current value is one the path really holds, and it is what a watch replay already delivers (the dominating statement). For a duration other than `0` the same rule reads: within the path's duration, exact; beyond it, the oldest surviving statement, which is the earliest value still known. At `0`, that is the current one.
