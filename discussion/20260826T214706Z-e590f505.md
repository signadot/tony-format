Question 3 is answered, and a question nobody asked has to be.

## 3, answered: the reads see the input

objPatchYWith recurses with `PatchWith(dy, patch, ctx)` where `dy = doc.Values[i]` -- the
document's OWN child, never anything rebuilt. Every doc node handed down during a patch is
the original with its chain intact, so doc.Root() mid-patch is the input document and

    {a: !get-path(root) b, b: !get-path(root) a}

is a swap. It is a guarantee that costs nothing, not a property to arrange.

## 7 (new): the answer is a VALUE, not a program

An op answers by handing something to f or pf, and both READ what they are handed:

    match   f(doc, V, ctx)     V is used as a PATTERN
    patch   pf(doc, V, ctx)    V is applied as a PATCH

Neither is what "the value over there" means, and each is wrong in its own way.

On the patch side that is a MERGE, not an install. `{sidecar: !get-path(root) ...main}`
would union main's fields into sidecar rather than make sidecar that value. The examples
filed above all fetch scalars, where merge and install agree, so it did not show.
`!insert` already has the phrase for the other reading -- "the value is what results" --
and that is the one this operator wants.

On both sides it means the DATA IS INTERPRETED. A fetched subtree is data from a document,
and a document carries tags: fetch something under a `!key(sku)` list and handing it to f
or pf reads `!key` as an operation. So what a get MEANS would depend on which tags happen
to be in the data it fetched, which is not a property anything should have. !raw is the
existing word for the other thing -- "treat the subtree as data, interpreting no operation
at any depth".

Both faces are one decision: the fetched value is installed as the result on the patch
side and compared as data on the match side, never re-read as a program. That also keeps
the operator's meaning independent of the document's tagging, which is the only way
`!get-path` can be reasoned about at the point it is written.

Which leaves 1 -- what a path naming nothing does -- as the one thing still open that
changes the implementation rather than a line of documentation.
