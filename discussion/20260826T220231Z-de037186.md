Question 1 decided: a path which names nothing is an ERROR, on both the match and the
patch side. Strict first; a tag param can relax it later if a real case wants it.

This departs from !at on purpose, and the divergence should be written down where both are
documented so nobody later "fixes" the inconsistency. !at relocates a PATTERN -- asking for
an a.b in a document which has none is a legitimate mismatch, and it reads the same way
!has-path does. !get-path answers with a VALUE: there is no value, so there is nothing to
compare against and nothing to install, and the only other answers available are the two
this family has already been burned by -- a null, which a match reads as "anything" and a
patch WRITES, or a silent no-match which says nothing about why.

One sub-case to confirm rather than assume: !get-paths over a wild path which reaches
nothing. Read strictly that is the same error. Read as a list it is a list of zero, which
is what !all over an empty container answers -- base.tony leans on that ("an empty object's
keys are all integers as much as a full one's are, and !all over nothing says so"). The two
operators differ here in a way that is not arbitrary: !get-path promises A NODE and cannot
keep it, while !get-paths promises a LIST and an empty one is a list. My read is that
!get-paths should answer the empty list and !get-path should error, but it is a fork worth
a sentence rather than a default.

An implementation note that follows from "another tag param later": do not read the args
positionally. `(root)` is optional, so a later `(root,<relaxation>)` and a bare
`(<relaxation>)` both have to parse, and args[0] being the anchor breaks the second. Read
each component by NAME -- !field(from,to) is positional because both are always present,
which is not the shape here.

With this, every question on the filing is answered. Ready to build.
