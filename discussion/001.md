The original writeup assumed one tokenizer bug with two faces, and concluded "the log is very
likely intact; fix the tokenizer and 3761 replays." **That conclusion is not safe.** A competing
explanation — the panic killed the process mid-write and the log was left badly framed — is
supported by the code, and it does not require any tokenizer bug at all.


`DLogFile.AppendEntry` (`system/logd/storage/internal/dlog/dlog.go:545`) does **two separate
writes**:

```go
if _, err := dlf.file.Write(lengthBytes); err != nil { ... }   // :568  4-byte header
if _, err := dlf.file.Write(entryBytes);  err != nil { ... }   // :573  payload
dlf.position = currentPos + 4 + int64(len(entryBytes))         // :578
```

No fsync on the data log. (The only `Sync()` calls in the package, `:193` and `:213`, are for
`dlog.state`, not for log data.) Process death between `:568` and `:573` leaves a **dangling
length prefix** — a header claiming N bytes with fewer than N following it.


`newDLogFile` (`:217`) opens the file, stats it, seeks to end, and takes

```go
position: stat.Size(),      // :244
```

There is **no scan to confirm the file ends on a frame boundary**, and no truncation of a torn
tail. `recoverCompactionArtifacts` (`:156`) handles compaction artifacts, not this. So a torn tail
is silently adopted as the next append point: the following entry lands immediately after the
garbage, and every frame boundary derived by walking from there is wrong — permanently, and in a
way that survives into the index.


This one worries me more than the panic window, because it needs no crash at all. The file is
opened **without `O_APPEND`** (`:219`, deliberately — snapshot writes need to seek) and appends use
sequential `file.Write`, so the OS file offset is the source of truth for where bytes land, while
`dlf.position` is bookkeeping.

If `:573` returns `n < len(entryBytes)` with an error, the function returns early and **`:578`
never runs** — but the OS offset has already advanced by `4 + n`. From that moment `dlf.position`
under-counts the real offset. The next `AppendEntry` writes at the real (later) offset yet returns
`currentPos = dlf.position` as the entry's position, so **the index records a position that does
not point at that entry's header**. That is exactly the observed symptom — reading a frame header
as document text — with no tokenizer involvement.


- The "log is intact, tokenizer fix alone recovers it" guidance in the description should not be
  acted on until the log is actually walked. Recovery may need tail truncation and/or index repair.
- The panic and the misalignment are still plausibly causally linked, but the link is *"an
  unrecovered panic anywhere killed the process while some goroutine was mid-append"* — not *"one
  tokenizer bug parses the same string wrong twice."* The read pump that panicked was not the
  goroutine writing.
- It raises the priority of the recover()-at-the-session-boundary item, since under this story an
  unrecovered panic is not just an availability event, it is a **durability** event.


Walk the log frame by frame from 0 (or from the last known-good index position), following
`4 + length` each time and checking that each landing site looks like a plausible header, treating
`BlobHeaderMagic` as `singleFileIter.next()` (`:690`) does. Then:

- **Walks cleanly until at/near the tail, breaks there** → write-side tear. Truncate to the last
  good boundary; the tokenizer is not implicated.
- **Breaks mid-file, at the record containing the offending string, with well-formed frames after
  it** → tokenizer over-consumption, as originally written.

Comparing the failing position 19459758 against the file size should be informative on its own —
if it is at the end, that is the write-side story.
