Addressed in 1d2538e (go-tony, ir/kpath).

**Ask 1 — path-against-path matching.** Added next to `AncestorOrEqual`:

- `func (p *KPath) Matches(o *KPath) bool` — equal-depth denotation. A wildcard
  segment in the receiver (`.*` `[*]` `{*}`) matches any segment of the same kind
  in `o`; concrete segments compare by value. So `review.seq[*]` Matches
  `review.seq[2]`, `review.*` Matches `review.onDone`. One-directional (p is the
  pattern) and reflexive (`p.Matches(p)` always holds, wildcards included), so a
  concrete segment in p does NOT match a wildcard in o.
- `func (p *KPath) MatchesPrefix(o *KPath) bool` — the ancestor-or-equal form (p
  may be shorter): `review.seq[*]` MatchesPrefix `review.seq[2].onDone`.

**Ask 2 — Wild() is head-only.** Added `func (p *KPath) HasWild() bool` (any
segment is a wildcard). `Wild()` keeps its head-segment-only semantics (it backs
`Type()`'s SegmentType) but now documents that explicitly and points at `HasWild`
for the whole-path question and `p.LastSegment().Wild()` for the last segment.

**Ask 3 — kind-spanning element wildcard: answered, deferred.** Matching is
kind-strict: a dense `[*]` does not match a keyed `(lint)` or sparse `{2}` element,
because `[*]` (ArrayEntry) and `(lint)` (KeyEntry) are different container kinds in
the model, and silently conflating them would make `[*]` mean "any element of any
container shape" — a broader, lossier predicate than callers of a dense-array glob
expect. There is no `(*)` in the syntax today, so a kind-spanning "any element"
wildcard is a syntax addition, not a matcher tweak. Left OUT of this change; if
verse (or anyone) needs to address a list positionally *or* by name under one
query, that wants its own issue proposing the syntax + semantics (does `(*)` also
span dense? does a bare "any element" token exist?). For now: query the two forms
separately, exactly as the workaround notes.

Also seconding the `filepath.Match` caveat — it is unrelated to these predicates;
`[2]` reads as a character class there, so glob-style matching over kpath strings
must go through `Matches`, never `filepath.Match`.

Asks 1 and 2 are complete with tests (the issue's table plus prefix and
Wild/HasWild cases). Leaving the issue open for the ask-3 decision — say the word
and I will either close it or split the kind-spanning-wildcard question into its
own issue.
