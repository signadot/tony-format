Numbers from downstream (verse), in case a concrete workload is useful. This is the ceiling
being hit in normal use rather than in a benchmark.

## Workload

`verse connect` federates a working tree into a per-session SCOPE: it writes a metadata entity
per file, and (today) installs a validator trigger per file, so each file also produces a
process whose lifecycle is mirrored back as several more writes. A scope opens its OWN session
(verse's LogdStore.Scope), so baseline and scope are two sessions writing concurrently.

    tree            300 files
    entities        300 metadata + ~1400 lines of process:instance state in the scope
    sessions        4 (baseline, two scopes, mount)
    client timeout  10s per request, flat

## What happens

    150 unscoped `entity put`s          →    0 dropped-response warnings
    connect, 300-file tree, one scope   → 1054 dropped-response warnings

First warning lands ~13s after connect starts, which is the 10s timeout plus dispatch — i.e.
requests issued in the opening burst expire, the client deletes its pending entry, and the
server's answers arrive afterwards with nothing to deliver to.

**It completes.** All 300 files are federated and readable ~20s later, and a 20-file tree
lands promptly. So this is the throughput ceiling as described — not a hang, not lost writes.
What it costs is that a client with any per-request deadline sees a wave of failures for work
that actually succeeded, and cannot tell the difference.

The asymmetry is the interesting part: zero warnings unscoped, ~1000 scoped, same store, same
machine. Two sessions contending on serial per-connection dispatch is enough to push a 10s
deadline over, where one session doing 150 sequential writes never comes close.

Downstream mitigations are ours, not yours (verse's `connect` spawning a validator per file is
the load, and docs/expose.md already argues for dropping that automatic reactivity). Filed the
unreadable log line separately as n1x09bryh12ks9aecsn0 — with pointer-formatted ids, none of
the above was visible from the logs.
