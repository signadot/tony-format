-b ## Fixed in `436de39` and `265cbc8`, released as `go-tony/v0.0.108`

## This issue was filed with the wrong diagnosis

I filed it as "eight scanner sites test `r == utf8.RuneError` without the accompanying
`sz == 1`, so a correctly encoded U+FFFD is rejected as bad utf8", and proposed a shared
helper across all eight.

That reads the policy backwards. Rejecting a raw `EF BF BD` is **intended**: a replacement
character arriving in a document means the text was already damaged upstream, and refusing
it is the right call. The conflation those eight sites make is the behaviour, not a bug, and
none of them needed to change.

Factually I was also imprecise in the original writeup: U+FFFD is a valid Unicode code point
and valid UTF-8 documents do contain it — it is what every lossy transcode emits, and
`utf8.ValidString` accepts it. Choosing to reject it anyway is a policy, which is a different
statement from "that is not valid UTF-8". The policy is sound; my justification for calling
it a bug was not.

## What was actually broken

The encoder did not honour that policy. `Quote` wrote U+FFFD out raw, so the library emitted
documents it then refused to read — a round-trip asymmetry with the encoder at fault, the
same shape as `dss3tkggh12kr4w2d1n0`, not a scanner problem at all.

Two places had to learn it, and the second only surfaced later:

- `436de39` — `Quote` escapes it as `�`, via the same `\uXXXX` path control characters
  already take. Both halves hold: `"a�b"` round-trips to the original value, and a raw
  `EF BF BD` is still rejected. Covered by `TestQuoteEscapesReplacementChar` and
  `TestRawReplacementCharStillRejected` — the second exists so nothing is quietly accepted
  just because the encoder learned to escape.
- `265cbc8` — a **multi-line** value containing U+FFFD no longer takes a block literal.
  Block literals write their content raw, so nothing inside one can be escaped, and the
  first fix only taught the quoted path. Such values take the quoted form, which escapes per
  line. This overrides an explicit `!literal` request, on the grounds that a formatting
  preference is not worth emitting a document that cannot be read back.

The second was found only because removing this bug's fuzz exclusion let
`FuzzEncodeParseRoundTrip` reach multi-line input again. The first fix looked complete and
was not.

## Verification

Both fuzz targets now run with **nothing filtered** — this bug was the reason for one of the
two exclusions each carried:

```
FuzzQuoteRoundTrip          79k execs, no exclusions    clean
FuzzEncodeParseRoundTrip    13.0M execs, no exclusions  clean
o b .../deploy/operator     33,264 lines               byte-identical
```

## Net

One condition in `Quote` and one in `doBlockLit`, instead of a helper threaded through eight
scanners. Closing as fixed, with the original framing corrected rather than left to mislead
whoever reads it next.
