-b ## Fixed in `265cbc8`, released as `go-tony/v0.0.108`

All fourteen chomping shapes round-trip; `"one\ntwo\n\n"` comes back unchanged.

## It was not the chomping rule

The `|+` arm writes a newline directly to the writer to close the block's last line —
`writeRaw` leaves the cursor mid-line, so `writeNL` cannot be used there. That newline was
correct. What was missing is that it never told the encoder where the cursor had moved to,
so the caller's `writeNL` fired as well and opened a second, empty line, which the parser
read as one more trailing line than went in.

I tried the two obvious fixes first and both failed, in opposite directions: deleting the
newline, and keeping the content whole instead of stripping and restoring one. Each made the
following key get absorbed into the block (`  z: s`). The arm was compensating for
`writeNL`'s skip logic, which keyed off state the raw write bypassed.

## The state had no name

`writeNL` skipped when `es.col == 0`. `es.col` was a column counter maintained at about two
dozen sites — every `writeString` paired with an `es.col += len(...)` — and **read in exactly
one place**, that comparison against zero. Two dozen arithmetic sites in service of one
boolean. `es.line` was incremented and never read at all. And two sites wrote bytes straight
to the writer without touching either, so the state could simply be wrong.

Replacing it with `atCol0` — *nothing written on this line and no indent on it either*, which
is what `col == 0` meant — made every `+=` a flag set that cannot be off by one, and made
this fix one line: record `atCol0 = true` after the raw newline, and the caller's `writeNL`
skips.

The fix did not get easier. The state got a name.

Each translation is 1:1, so behaviour is unchanged by construction, and the manifest oracle
confirms it — byte-identical after the refactor alone, and again after the fix.

## Verification

The exclusion this bug forced is gone: `FuzzEncodeParseRoundTrip` compares multi-line values
exactly again and runs with nothing filtered.

Note this leaves the two direct-to-writer sites in place (`encodeBLit`'s `|+` arm and one
other). They are now correct, but they are correct by hand rather than by construction —
`writeString` takes no `EncState`, so the flag cannot be maintained there without changing
its signature at ~40 call sites. That was judged not worth it now; it is the remaining way
this class of bug could return.
