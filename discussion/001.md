-b ## Fixed in `15f2ca6`, released as `go-tony/v0.0.107`

`NeedsQuote` now quotes a value that is bare `-`, that opens with `<`, `>` or `|`, or that is
a sign followed by a digit.

The second group was the quieter half and was not in the original report: `-1`, `-0` and
`-1.5` parsed cleanly and came back as **Numbers**, so a string went in and a number came out
with no error anywhere. `-00` did not parse at all. The leading-digit check missed all four
because the sign comes first.

## Tests

- `TestEncoderOutputAlwaysReparses` sweeps every printable ASCII byte alone and at each end
  of a word — complete for the single-character class, not a spot check.
- `TestNeedsQuoteAgreesWithRoundTrip` asserts the property rather than the list, so a new
  sigil in the tokenizer fails without anyone remembering `NeedsQuote` exists. That is the
  guard against this recurring: the fix is still a mirror of a dispatch that lives elsewhere.
- `FuzzEncodeParseRoundTrip` found the first case in 51 executions and is clean over 11.5M
  after the fix.

All three check that the value comes back **unchanged**, not merely that the output parses.
The weaker property was passing while `-1` was silently becoming a number.

## Verified against a real corpus

`o b /Users/scott/Dev/github.com/signadot/signadot/sandboxes/deploy/operator` — 33,264 lines
of Kubernetes manifests — is **byte-identical** before and after, exit 0 both.

That is a no-regression result more than coverage: the corpus contains no string scalars in
the affected classes. It does cover the property most at risk of over-reach, though —
`default: -1` at line 4763 is a genuine negative number in a CRD and stayed unquoted. A rule
written as "quote anything starting with `-`" would have turned it into `"-1"` and changed a
CRD default from int to string.

## Two exclusions in the fuzz target

Both tracked, both there so a known gap does not mask a new one:

- `prfzxpa2h12ks3vscxn0` — a correctly encoded U+FFFD is rejected as bad utf8.
- `pyhfz6h6h12ks3cjd1n0` — `|+` block chomping adds a trailing newline, so multi-line values
  are compared with trailing newlines trimmed. Found by this same fuzz target once it was
  strengthened to check fidelity; filed separately as it is a different part of the encoder,
  and it is a suspect in the unreduced `data6-imbalanced` corpus described in this issue.

Tightening either exclusion back is the test for those fixes.
