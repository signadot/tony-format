Recording no-op writes has a bearing on compaction semantics that argues against
suppressing them, in two connected ways.

COMMITS ARE THE CLOCK. Snapshot creation is activity-driven, not time-driven:
SnapshotConfig triggers on MaxCommits (commits since the last snapshot) or
MaxBytes (active log size), and the server counts commitsSinceSnapshot.
Compaction then buckets the resulting snapshots into time tiers whose intervals
grow by a multiplier. So the wall-clock density of retained history is currently
paced by commit volume.

Suppress no-ops and a store whose traffic is mostly reconcile writes stops
producing commits, so it stops producing snapshots, and the deep tiers thin out
in wall-clock time. That loses nothing for state reads -- a snapshot taken
before a quiet period answers "state at T" exactly for every T inside it,
because nothing changed -- but the snapshot cadence detaches from wall-clock
activity, which is a change to a retention model that is commit-paced by
assumption rather than by decision.

THE WINDOW'S CONTRACT. Compaction promises history fidelity within the cutoff:
every patch kept, exact to the commit. If no-ops never enter the log, that
promise describes a filtered stream, and the log can no longer answer "when did
anyone last assert this value?" For a reconcile system that is the
post-incident question, and it is exactly what suppression discards.

Against both: the retained window's disk is spent on entries carrying no change,
and log-size-driven switching and compaction arrive sooner.

So the question may not be "should a no-op be stored" but "is the retained
window a write history or a state history" -- and those plausibly want different
answers at different depths. One resolution worth weighing: keep no-ops inside
the cutoff, where the window is about write fidelity, and make them the first
thing dropped beyond it, where the tiers are about state. That is a compaction
policy change rather than a write-path change, and it leaves the commit
semantics (and the tick) alone.
