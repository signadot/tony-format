-body Not a bug — closing as working-as-intended.

Reviewed with the reporter. The request-timeout path (session.go handlePatch, timeout>0) spawns patcher.Commit() on a goroutine and, on timeout, returns ErrCodeTimeout to the client. Crucially the commit is NOT dropped: when the multi-participant tx resolves, Commit() runs doCommit on that goroutine, which performs WriteAndIndex (durable append + index + snapshot) AND Notify (watch fan-out). The server stays fully self-consistent — log, index, and watch deltas all reflect the commit. Only the ack to the one participant whose deadline fired first is lost.

That loss is inherent to distributed commit (two-generals): once a participant has submitted its patch, the outcome is decided collectively by whether the other participants arrive before Tx.Timeout. A request timeout is 'I gave up waiting for the response', not a clean withdrawal of already-submitted intent. Cancelling on timeout would either race the coordinator with the same uncertainty, or wrongly abort a tx the other participants successfully joined. The honest signal is 'unknown outcome — go check', and the correct recourse is client-side: re-read after a timeout, made idempotent by the CAS Match precondition logd already provides.

Two claims in the original finding were wrong: onCommit/snapshot are NOT skipped (they fire on the commit goroutine), and there is no avoidable server-side 'phantom write' distinct from inherent ack-loss.

The only real residual — the commit goroutine parked forever when Tx.Timeout=0 (Commit() never returns) — is the no-timeout-blocks-forever scenario already tracked by hqhyyat8, not a separate issue here.
