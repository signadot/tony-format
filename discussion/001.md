## What you get

```go
var why tony.Explanation
ok, err := tony.Match(doc, pat, tony.Explaining(&why))
// why.Failures[i]: Path (kpath, with !all indices), Op, Reason,
//                  Expected *ir.Node, Found *ir.Node, Causes []*Frame
```

`tony.Tracing(&why)` is the same channel with the other polarity kept: `why.Matches` is the operator frames which matched, in walk order, and which alternative of an `!or` matched is the cause under it with `Matched` set. `why.Root` is the whole frame tree either way; `Failures` is the flattened reading of it.

`schema.Validate` now returns a `*schema.ValidationError` carrying the `*tony.Explanation`, and its `Error()` names the paths. Your six rows, verbatim, are `TestValidateSaysWhy`:

```
ok             -> nil
bad-enum       -> class: or: expected !or [bug nit risk], found critical
missing-field  -> severity: absent: expected !or [low high]
wrong-type     -> why: irtype: expected !irtype string, found 3
two-failures   -> class: or: expected !or [bug nit risk], found critical
                  severity: absent: expected !or [low high]
extra-field    -> nil
```

`!all` over a list names the element: `findings[1].severity: or: expected !or [low high], found bogus`.

## How it avoids being wrong by default for anything new

No operator was changed. Two rules in the walk do the work:

1. **A frame which matched is dropped, with everything recorded beneath it.** That alone keeps the losing branches of a *successful* `!or`, and the sub-matches an `!not` needed to fail, out of an explanation of something else.
2. **Descend through an operator frame with exactly one failed cause; stop at zero or several.** `!all` short-circuits, so it has one cause and passes through to the element which failed. `!or` which rejected everything has three, and reports itself with `Expected` the whole `!or` node -- its alternatives are not defects to repair. An operator added after this commit reports itself: coarse, never wrong. An operator which judged something it *synthesized* rather than a node of the document (`!field` on a field name, `!tag` on a tag) also stops there, since what is beneath it has no path in the document.

Paths come from the document nodes' own parent links, so indices chosen inside `!all` cost nothing, and `Found` is the node, not a copy. `Explanation.String()` bounds each rendered node at 120 bytes for the prompt case; `Expected`/`Found` are `*ir.Node` for everything else.

## Your four, and one caveat

1. kpath with list indices -- yes, including inside `!all`.
2. `Expected` as `*ir.Node` -- yes, unrendered, and it is the whole tagged node.
3. absent vs present-but-wrong -- yes, `ReasonAbsent` vs `ReasonType`/`ReasonValue`/`ReasonOp`.
4. all failures -- **structurally**: every field of an object which fails is reported, so one repair round can fix them all. **Operators keep their short circuit**: an `!all` over twelve elements names the first bad one, not all of them. That is the walk the operator does, and lifting it would mean teaching each operator about explanations. Documented on `Explaining`; say the word if the `!all` case matters and it can be done for the conjunctive operators specifically.

Two invariants are tested rather than assumed: asking why never changes the verdict, and never turns a plain `false` into an error by walking into pattern the match would have stopped short of. `Validate` runs the cheap match first and explains only a rejection, so a document which validates pays nothing; plain `Match` benchmarks unchanged.

`MatchConfig.Comments` and `.Tags`, and `MatchComments`/`MatchTags`, are deleted -- inert, and unused everywhere.
