## Refinement (discussion) — separate mount address + reads route through controllers

Two corrections to the analysis above.

### 1. Mount protocol on a separate TCP listener
docd serves the MOUNT (controller) protocol on its own TCP address, distinct from
the client address. This replaces the "split connection role by first message" idea
in component A: two listeners, two session constructors.

- client listener (e.g. :9124) — logd session protocol, verbatim.
- mount listener (e.g. :9125) — MOUNT protocol (logd-shaped + additive `mount`).

Strengthens switchability: the additive MOUNT protocol never shares a socket with
the logd-compatible client face, so there is no envelope multiplexing to reconcile.
`o docd serve` grows a second `-mount-addr`; `o sys up` composes both; `tcp.go`
becomes two listeners.

### 2. Reads route through the owning controller (NOT logd passthrough)
Supersedes the earlier "MATCH/WATCH -> passthrough to logd" in components A and D.
For the connect-controller dogfooding case, a client read of mounted content MUST
go through the controller. If it resolved from logd, the controller would have had
to warehouse every file's bytes in logd first — defeating "index, not warehouse /
serve on demand."

Revised routing model:

> A mount is an owner that answers for its subtree, for reads AND writes. Only
> paths not under any mount are served from logd directly.

Consequences:
- MOUNT is bidirectional for reads, not just PATCH: docd->controller MATCH/GET. The
  controller answers content reads on demand (reads the file) and never writes those
  bytes to logd.
- Controller-side Handler grows HandleMatch alongside HandlePatch; DocdSession
  dispatches both.
- docd is an authority-routing layer, not a transparent logd. It keeps a logd
  connection only for non-mounted paths and the change stream.

Switchability rule #1 refined: the client speaks the identical protocol/LogdSession
API against docd or logd (that is the switch), but reads are NOT a transparent logd
passthrough — a mounted-path read is controller-served. Same client code, richer
data. That is the point of docd.

### Open questions (M1 recommendations)
1. WATCH routing — index/change-stream watches live in logd; content watches would
   come from the controller. M1: keep WATCH on logd (index), serve content via
   controller-routed MATCH; defer content-watch.
2. Index vs content split — don't bake entity-verse semantics into docd core. Let
   the controller own reads for its subtree and choose the source (disk for content,
   its own LogdSession for index). docd just routes by path.
3. Read caching — docd could cache controller reads keyed on change-stream commit to
   avoid hitting the controller every read, but that reintroduces a second copy the
   design warns against. No caching in M1; if added, invalidate on the change stream,
   never TTL. [OPEN]
4. Read/commit coherence — a controller-served content read should echo the commit it
   corresponds to, so a client can pair (metadata@commit, content). Carry `commit` on
   the routed MATCH. [OPEN]
