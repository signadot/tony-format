## Repro (probed directly against logd via LogdSession)

Scope s1 writes a.x=5, then baseline writes a.x=99:

    AFTER s1=5:    scoped-read a.x=5    baseline-read a.x=null   (correct: scope write isolated)
    AFTER base=99: scoped-read a.x=99   baseline-read a.x=99     (BUG)
    s1 watcher deltas (NoInit watch on a.x): [c1:5, c2:99, c3:6]

## Expected (sticky COW)

Once scope s1 has written a.x, it owns that path in its view: a later BASELINE
write to a.x must be shadowed in s1. So after base=99, scoped-read a.x should
still be 5 (s1's value), and the s1 watcher should NOT receive the baseline 99
delta for that path.

## Actual

- scoped-read a.x returns 99 after the baseline write — the baseline write
  overrode the scope's prior value (read side).
- the scoped watcher also receives the baseline 99 delta (server/watch.go
  matchesScope delivers all baseline events to a scoped watcher).

## Impact

Breaks COW isolation for dogfooding: a scoped (sandboxed/branched) client cannot
rely on its writes surviving concurrent baseline writes. Surfaced while validating
docd scope-across-mounts (branch docd-followups); docd correctly forwards scope,
so this is purely a logd storage/watch issue.

## Suspects

- read side: storage ReadStateAt scope overlay — appears to pick latest-commit
  across baseline+scope rather than shadowing baseline once the scope has written
  the path.
- watch side: server/watch.go matchesScope — a scoped watcher gets baseline
  events even for paths the scope has overridden; should be filtered consistently
  with the read overlay.

Note: I initially (wrongly) read this as an intentional latest-commit-wins model;
it is a bug.
