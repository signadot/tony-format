Faces 1, 2 and 3 are closed, plus a fourth found while fixing them.  Face 4 is

## 1. Encoder emitted unparseable documents — fixed

`strconv.FormatFloat(f, 'f', -1, 64)` at `encode/encode.go:763` wrote the
largest float64 as its 309 digit decimal expansion.  `'g'` switches to an
exponent where a decimal expansion would run long.

```
1.7976931348623157e308  ->  1.7976931348623157e+308   (was 309 digits, unparseable)
```

## 2. Integral floats retyped — fixed

`'g'` alone still writes 1.0 as "1", so a ".0" is appended when nothing else
marks the value as a float.

```
1.0 -> 1.0     1e2 -> 100.0     3.0e2 -> 300.0     (were 1, 100, 300)
```

Every one of these now satisfies `Parse(Encode(n)) == n`.

## 3. Signed zero broke equal-implies-same-hash — fixed

Fixed in `Hash`, not in `DeepEqual` — and that direction matters.  `DeepEqual`
uses Go's `==`, where `-0.0 == 0.0`, so they are one value and `Hash` was the
one disagreeing.  `ir/hash.go` normalises the zero before `Float64bits`.

That also means the encoder writing both as "0.0" was already correct and is
kept: one value, one text.  The suggestion in this issue to "make DeepEqual
sign-aware or make Hash normalize it" has a right answer rather than two.

## 4. Infinity and NaN — found while fixing the above

Not parseable, but the Go API can build them, and the encoder wrote "+Inf" —
putting back the unparseable output face 1 is about.  Encoding one is now an
error.

## 5. Numbers beyond int64/float64 — recorded, not fixed

Wider than this issue described.  It is not only `1e400`:

```
1e400                           rejected   beyond float64
123456789012345678901234567890  rejected   beyond int64; encoding/json rounds it
9223372036854775808             rejected   int64 max + 1
```

All three are valid JSON, so `docs/tony.md:10` was overclaiming in three ways.

Resolved as a **current implementation limitation** rather than a property of
the format: a Tony number is a JSON number, and big.Int/big.Float can be added
later.  `docs/tony.md` now says so under Number Range, and
`TestNumberRangeLimitation` pins the current behaviour so that adding
arbitrary precision numbers has to say so.

Rejecting is the conservative reading in the meantime — Go's `encoding/json`
rejects the first two and silently rounds the third to `1.2345678901234568e+29`.
