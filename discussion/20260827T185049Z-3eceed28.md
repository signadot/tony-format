# P1 status: the gap comment 004 named is CLOSED; one other remains

Checked against the tree today.

## closed: a write now carries the keying the index records

Comment 004 left this open: "the schema route still writes index paths its own patch cannot
resolve. tx/auto_id.go injects the id FIELD into each element but no !key(id) tag, so the
index records items(\"<id>\") while entry.Patch.GetKPath(...) finds nothing."

It is closed, by `tx.InjectKeyTags` (storage/tx/key_tags.go), called from coord.go:421 --
after InjectAutoIDs at 415, so the id exists before the tag goes on. The decision the
question needed ("auto-inject !key based on schema, or reject patches without?") was taken
and is stated where it is implemented:

> Injecting rather than rejecting is a choice about whose job it is: the schema says these
> elements have identities, so a client that names one should not also have to repeat how
> identity works on every write. A patch that carries its own !key for the same array is
> left alone if it agrees, and refused if it does not.

Both declaration routes are covered, which is what closes the auto-id half specifically --
api.Schema.LookupKeyField:

> Both declarations mean "keyed": an explicit !logd-key, and an !logd-auto-id, which is
> keying plus generation.

`!logd-key` is the client-supplied half added since comment 004 (docs/logd/keyed.md), and
Validate refuses a schema declaring two identities for one array.

So the merge now identifies elements the way the index does, which is the property the whole
approach rests on -- and the property a LOWERED delta would rest on even harder, since
`Diff` over op-free state has only the tag on the patch to go by.

## still open: RootPatchAt cannot root at a keyed path

The plan's other named P1 gap is live, reproduced today:

    tx.RootPatchAt(`items("A")`, {qty: 5})  -> err "ir node unspecified"
    tx.RootPatchAt(`items`,      {qty: 5})  -> items: {qty: 5}
    tx.RootPatchAt(`a.b`,        {qty: 5})  -> a: {b: {qty: 5}}

A key segment carries the key VALUE while building a patch needs the key FIELD. The
workaround -- root at the array and carry a one-element keyed list -- is used twice, in the
stepping harness and in the overlay, and the plan asks that P1 either teach RootPatchAt the
key field or factor the helper out "rather than let it be rediscovered a third time".

## what that leaves

P1's substance is done: keying is single-sourced (ir.Node.KeyField / ir.ElemKey, five call
sites), the persisted schema is the authority (schema_authority_test.go), and a write carries
its own keying. What remains is the RootPatchAt helper, which is ergonomics rather than
soundness -- nothing is wrong today, it is discovered and worked around each time.

So the keying prerequisite the lowering needs (fdf4bdd: "P1 is now a prerequisite for the
storage format itself") is met.
