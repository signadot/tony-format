Fixed in 6fb4a4a. LOGD_SEEDS=500 LOGD_LOWERING=all now breaks 0 of 6127 claims (2 before either fix, 1 after the first).

ApplyPatches has TWO folds and c3811ef only fixed one:

- no base events: fold whole patches from null (the four-op reduction in the original report);
- a snapshot under them: collect the node at each patch root and fold that path's patches into it, applyPatchesToNode.

Both carried the previous patch's marker into the next fold. Reverting either fix alone now fails exactly its own regression test and not the other's, so neither covered the other.

The second surfaces differently, which is why it outlived the first fix and why I chased it in the wrong place twice. A merge composes the patch's tag ONTO the document's, so the marker leaves a fold wearing the document's own presentation:

    !delete(bracket) applied to a document tagged !bracket.logd-patch-root
    -> "didn't match bracket"

The first route fails a type check (bracket vs !bracket.logd-patch-root at $); this one fails an OPERATION's tag check. Same leak, different detector.

Reduced: four baseline writes at the root, snapshot after the first, no scope and nothing keyed:

    "" <- # note / {k0: 0}   [snapshot]
    "" <- !rename [{from: "k0", to: "k0"}]
    "" <- {k1: 4}
    "" <- !delete

On the doubled tag noted in my previous comment: it is NOT a producer marking twice. Instrumenting every MarkPatchRoot call with a stack trace shows every call in the reduced stream lands on an unmarked node -- already=false throughout. `!logd-patch-root.logd-patch-root` composes during a fold, from the same leak. That instrumentation is what found this; two rounds of reading the code had pointed at the wrong places.
