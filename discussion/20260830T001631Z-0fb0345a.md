Closing conditions changed, so re-stating where this sits.

The overlay is deleted (73e2637), and with it NewScopedWatchStepper -- so a scoped watch does recompute per event again, which was the half of this issue I said remained. But the recompute is no longer the thing this issue was about.

A scoped watcher's per-event work goes scopedDocAt -> readDocAt -> ReadSubtreeRootedAt, which is a read AT THE WATCHED PATH, and scoped reads narrow now. Measured on a watcher whose path is quiet while the scope is busy elsewhere:

    N accumulated scope writes:   50       100      200      400
    recompute, wide (before):     1.06ms   1.52ms   3.43ms   6.78ms
    recompute, narrow (now):      41us     43us     51us     58us

So the per-event cost is effectively flat in the scope's accumulated history, which is what a stepper was for. A stepper removes the READ; narrowing made the read cheap instead, and without materializing a scope layer for anything to be derived from.

What is still literally true in the title -- a scoped view cannot be STEPPED -- remains true, and the reason has not changed: a scope's writes apply last and shadow baseline stickily, so folding a baseline patch into a materialized scoped document lets baseline overwrite a leaf the scope owns. Whether that is worth solving is now a different question than when this was filed, because the cost that motivated it is gone. Worth deciding rather than assuming.
