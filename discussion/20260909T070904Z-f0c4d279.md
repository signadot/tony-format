-m DESIGN DISCUSSION, 2026-09-08/09. Where it landed, what was ruled out, and what is still open. Nothing built.

## What it becomes

LIST GENERALISES TO NAV, which streams EVENTS rather than elements. `list` is then the special case -- nav at depth 1, keys only -- and recursive application falls out of depth rather than needing its own request. `match` stays exactly as it is for the ordinary small read: one round trip, one body.

The reason nav is the better object is that it finishes something the rebuild left half-done. The store's currency is already events: Read answers a cursor, chosen in phase 3 because a signature returning a document cannot express a bound. Phase 5 then had the server encode a match body straight off that cursor, so no node is held SERVER-side -- but the response is still one frame, so the client still receives the whole subtree at once. The bound stops at the wire. Nav carries the cursor across it, and "one read, at a path, answered with a cursor" becomes true end to end.

## Ruled out, with reasons

A NAV ABOVE A MOUNT IS AN INVALID REQUEST, to start with. That removes composition entirely -- merging child names across owners, dedupe, ordering across routes, and mid-stream membership changes -- which was the bulk of the work and all of the undecided design. Breadth at a mount boundary is not the fanout problem, and recursion across one is the client's to do by navving each side.

NO BATCHING IN THE WIRE. One event per message, as watch already does. Backpressure already exists and needs no protocol construct: send blocks on a full outgoing channel, the writer blocks on the socket, so a nav producer throttles to whatever the client actually consumes, through TCP. The cost is bandwidth AND a per-message parse -- server-side batching recovers syscalls but not the `{nav: {id: ...}}` framing repeated per event -- and that cost is accepted as natural within the existing session constructs.

NO SERVER-SIDE PER-STREAM SLOW-CONSUMER KILL. Watch's bounded buffer exists to protect the COMMIT PATH: Broadcast runs on the tick's dispatcher and must never block, so a full buffer drops the watcher. Nav has no shared producer -- its producer is a per-request goroutine walking a cursor -- so blocking harms only itself, and killing the stream protects nothing. Selective slowness only exists on the consuming side anyway (one socket, one byte stream), and libctl already handles it in the right place: Watch.deliver fails a watch locally when its own channel fills.

## The single writer, which is a latent defect independently of nav

Two failure modes, and only one is fixable. A client not reading at all blocks the socket and stops everything, which is correct. A client reading SLOWLY makes small responses queue behind bulk ones -- a nav starving a patch acknowledgement on the same session -- and that is the real defect. It is purely write-side: the request side is already parallel, since reads dispatch off the loop under readSlots.

Options, cheapest first, the first two worth doing whether or not nav lands:

1. PRE-ENCODE OFF THE WRITER. writer() currently calls resp.ToTony itself, so a large response's encoding also occupies the one serialization point. Phase 5 already established the alternative for match bodies (encodedMatch builds the frame in the producer goroutine, sendFrame hands the writer finished bytes). Generalising that so the writer only ever writes is small and has no wire impact.
2. CLASS THE QUEUE AND SCHEDULE IT. Split outgoing into control/response and bulk, and have the writer prefer control -- weighted round-robin rather than strict priority, so sustained small-request load cannot starve bulk. This is what actually fixes the complaint. With it in place, a nav producer blocking on a full bulk queue is CORRECT and contained.
3. Withdrawn (see above).
4. PARKED: bulk on its own transport. xap is the candidate rather than something invented -- mature and fast -- but it is a dependency decision and a binary protocol, and the session's hand-speakability is an advertised feature (the docs show speaking it at a prompt). The shape that keeps both is to leave the interactive text session as it is and negotiate a bulk side channel carrying only nav-shaped traffic. Not worth spending until 1 and 2 are in and something measured says the single connection is the limit.

Worth noting that splitting RESPONSES across transports does not threaten read-your-writes, which rests on request dispatch order through the single reader loop. What it costs is cross-stream response ordering.

## What a paused nav holds

The fold goroutine is ALREADY independent -- newFoldCursor runs ApplyPatches in its own goroutine feeding a 64-event channel, which is decision 2's push-to-pull adapter. A paused nav parks it on that channel. Cancellation already works properly there: chanSink.WriteEvent selects on the send and on done, and Close closes done and drains, so a parked fold goroutine is promptly interruptible. Nav only has to actually call Close.

Converting the processor to PULL-MODE would free the goroutine's stack but not the base reader (an open snapshot/file handle) or the projected patch set, which the walk's POSITION pins either way -- so it buys less than it appears to. Pull-mode stays what the plan already says it is: the follow-up to decision 2, justified by a profile showing goroutine-per-cursor, not by this.

The only thing that genuinely frees a paused walk is RESUMABILITY: drop the reader and the projected set, and re-seek and re-fold to a saved position on resume. That trades held resources for re-fold cost, and it is a protocol feature (a position token in the request) rather than an internal one.

The cheap real bound is ADMISSION. Watches are admitted deliberately and match reads are capped by readSlots, but a nav is long-lived and holds a cursor for its whole life, so without a cap a client can pin that many base readers. A limit on concurrent navs per session, refused at request time with its own code, is cheaper than any of the above.

## Still open

- THE CONSUMER SHAPES THE REQUEST. verse's !list-paths is the motivating case -- `id: "*"` walks a whole kind, with a value predicate, and its own docs flag truncation as "the fourth and still unpaid". Predicate pushdown, ordering and truncation should be designed in before the shape freezes rather than retrofitted into a stream.
- ORDERING has to be decided, not inherited: document order is natural for a single owner, and the alternative is declaring the stream unordered.
- COMMIT PINNING: a nav should pin a commit as a read does, or it walks a moving document.
- KEYED ARRAYS: children are stored as names like (sku=A) while the client's vocabulary is an array, so elt should carry the client's spelling, consistent with RaiseState and ident.CanonicalPath.
- PROTOCOL BUMP to 3 for a new operation. An unknown op does fail honestly today (dispatch's default answers invalid_message), but a client should not have to discover support by trying.

## What it does not need

Composition work, given the mount rule. And no new storage machinery: the cursor streams already, stream.State already tracks depth and path, and stream.Event already carries tony field tags (t, a, k, ik, s, i, f, b, c), so the event wire form exists and stays legible like the rest of the protocol.
