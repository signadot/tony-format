## 18. A type ALIAS to `*ir.Node` resolves to `int` in the same package, and errors across one

Against **v0.0.92**. Same family as items 3, 8 and 14 — a type the resolver cannot place
becoming an integer — but worth its own entry because the type in question is `*ir.Node`
itself, the one every open-valued field wants, and because the two spellings fail
differently.

```go
// spike/use/use.go
package use

//tony:schemagen=spike-direct,notag
type Direct struct {
	P *ir.Node `tony:"field=p"`      // spelled directly
}

type Local = *ir.Node

//tony:schemagen=spike-local-alias,notag
type LocalAlias struct {
	P Local `tony:"field=p"`         // the SAME type, via a same-package alias
}
```

`tony-codegen -dir .` exits 0 and writes:

```tony
define:
  p: .[tony-base:ir]          # Direct — correct
---
define:
  p: .[int]                   # LocalAlias — the same type, described as an integer
```

```
spike/use/use_gen.go:108:32: cannot convert s.P (variable of pointer type Local) to type int64
spike/use/use_gen.go:148:10: cannot use int(*fieldNodeUnwrapped.Int64) (value of type int) as Local value in assignment
```

So the same type, spelled two ways, produces a correct schema in one case and `.[int]` plus
non-compiling Go in the other. The build failure is the lucky part — a published schema
claiming `int` for a field that accepts any tony value is the part that would have been
silent, since nothing checks a signature against the code that generated it.

**Across a package boundary the same alias errors instead**, which is at least loud:

```go
package al
type Payload = *ir.Node
```
```go
//tony:schemagen=spike-cross-alias,notag
type CrossAlias struct { P al.Payload `tony:"field=p"` }
```
```
failed to resolve field types: failed to resolve type for field "CrossAlias"."P":
failed to find type "Payload" in package ".../spike/al": "Payload" is not a named type
```

The cross-package behaviour is defensible as-is (an error beats bad output). The
same-package one is the defect: it takes the identical construct and, instead of the same
error, guesses `int`.

**Why it matters beyond aesthetics.** An alias is the natural way to give an open payload a
domain name — `type Payload = *ir.Node` reads better at hundreds of call sites than
`*ir.Node` does, and it is an alias precisely so that codegen sees the underlying type. That
is the one thing it does not do.

**Workaround in verse:** spell `*ir.Node` directly in any schemagen'd struct field. verse's
`entity.Payload` is an alias for `*ir.Node` and is used throughout the codebase, but the one
struct field that codegen sees (`api.PutEntity.Payload`) spells the underlying type instead
— so the alias survives as the domain vocabulary everywhere except the place a generator
looks.

**Suggested fix:** resolve aliases to their target before type resolution, in both the
same-package and cross-package paths. Failing that, make the same-package path raise the
cross-package error rather than falling back to `int` — the integer fallback is the recurring
shape behind items 3, 8, 14 and this one, and each time the cost is that a resolution failure
is reported as a plausible wrong type instead of as a failure.

Not a new defect, a retraction: I earlier believed this alias case produced *map-shaped* code
and an `object(object)` schema. It does not — that was a stale generated file being read
