Root cause: DiffString and the two appliers disagreed about what a strdiff key means.

DiffString keyed every operation by a byte offset into the result string, in both modes -- the multiline flag only tuned diffmatchpatch's internal speedup, it never changed the encoding. PatchStringMultiLine read those keys as line numbers, so every multiline diff panicked, not just this one: "one\ntwo\nthree" -> "one\ntwo\nthree\nfour" is a one-operation diff and panics. Two more bugs shared the cause. PatchStringRunes read the keys as rune indices, so any string wider than ASCII patched to the wrong text silently. And a !delete advanced the applier by one however much it deleted, so a second operation after one landed in the wrong place -- forward and in reverse.

Fixed in c6ecfa6. A key is now a position in the sequence the two strings share, counted in the unit the tag names: a rune under !strdiff(false), a line under !strdiff(true). A delete takes its own length and a !replace takes as many positions as its longer side. That is DiffArrayByIndex's convention counted in units rather than elements, and it has to be, because Reverse swaps from and to and rewrites no key. !strdiff(true) is now a real line diff. Keys of currently working single-operation diffs are unchanged.

For verse: this needs a go-tony release, the panic was against v0.0.123. Skew against a server which has not been updated degrades from a crash to a failed patch -- the applier now errors on a key past the end of the document rather than indexing off it.
