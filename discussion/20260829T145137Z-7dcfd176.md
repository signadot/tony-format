Tried the fix that worked for the claim -- build the overlay as a patch, place
statements instead of applying them -- and it does not carry over. Reverted, with
what it showed, because the reason is about the overlay's shape rather than about
the union.

claimDelta was fixable that way because its claims are (path, statement) pairs at
disjoint paths and nothing else: tx.MergePatches nests them, interprets nothing,
and that is the whole construction (48250f3).

The overlay is not that shape. Its owned-path half decomposes the scope's state
into the DEEPEST owned paths -- deliberately, so that stating an ancestor does not
take baseline's siblings into the scope's ownership -- and then unions each one
in. That decomposition is only coherent because the union APPLIES: application is
what resolves a deep statement back into ordinary structure. Three things it was
resolving, each of which surfaced immediately when the union stopped applying:

  1. An arraydiff spine. Rooting a statement at an owned path like
     rules.value.let[0].tip builds an !arraydiff for the [0] segment, which is
     relative by construction. Applied, it resolved into data on the way in and
     never reached the log. Placed, it stays, and ValidateForStorage refuses the
     overlay -- correctly.

     Truncating owned paths above any position fixes that one, and is the same
     rule ClaimPaths already uses: a position is not an identity, so the array is
     what the path can name.

  2. A statement beneath ESCAPED data. A scope writing

         rules <- !raw {value: !let {let: [{tip: abc}], in: {state: open}}}

     holds a !let at rules.value as DATA, and the index records paths inside it
     (mergeop.OperandPaths says the escape hides operations, not paths), so
     rules.value.let and rules.value.in.state are owned. The diff half states
     rules.value whole and escaped; the owned statements are inside it. Applied,
     they merged into the escaped value. Placed, the deeper statement and the
     tagged ancestor are two statements about overlapping paths, and there is no
     precedence rule that is right for both -- taking the ancestor drops the
     re-statement, taking the descendant drops the tag, which is what the test
     caught.

  3. Keyed elements. absence at items("G") cannot be rooted at all: RootPatchAt
     refuses a key segment by design, and RootKeyedListAt takes VALUES, so there
     is no way to say "this element is not in the list" with what exists.

So the fix is not a change to the union. It is a change to how the overlay
decomposes ownership: the descent has to stop where a path stops being nameable
-- at a position, at an operation, at a keyed element -- which is the same rule
ClaimPaths applies to a patch, and then the union has nothing overlapping to
resolve and can be a construction. (1) and (2) are the same rule; (3) needs a way
to state an element's absence in a keyed list, which the vocabulary may not have.

Until then the union stays api.NextState, with a patch in the document position,
and the delete is still lost.
