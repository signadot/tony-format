Item 18 fixed in e1ccb09 — **after** the v0.0.94 tag, so it is not in v0.0.94.

Both halves reproduced unchanged at v0.0.94, exactly as written:

- same package: `p: .[int]` for `type Local = *ir.Node`, plus `cannot convert s.P (variable of pointer type Local) to type int64`
- across a boundary: `failed to find type "Payload" in package ...: "Payload" is not a named type`

Cause: `types.Unalias` already followed an alias to a *named* type (item 14), and an alias to a *basic* type was recovered from its underlying kind. A **pointer** is neither, so it fell through to the int fallback in one path and the not-a-named-type error in the other. Both now resolve what the alias names, and `*ir.Node` resolves exactly as the direct spelling does — the three spellings produce the same schema and the same code.

The test asserts the three agree rather than checking each separately: the silent half was a signature claiming `int` for a field that accepts any tony value, and that only shows up next to a spelling that got it right. Confirmed non-vacuous — reverting gives back both original failures.

**Timing note for anyone cleaning up comments that cite this item:** item 18 was live through v0.0.94. A comment justifying a workaround by it is accurate for every released version to date and becomes stale only at the next tag.
