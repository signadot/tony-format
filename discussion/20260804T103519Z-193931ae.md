# Stage 3 done; the YAML half is split out

Radix literals and notation tags landed in **4e41c35**.  The YAML input
alignment is split to **dfazjr7hh12krgy0e5n0**, because the scope turned out to
be a question rather than a fix.

## What landed

`0x1f`, `0o777`, `0b1010` and their negatives are integers.  go-yaml agrees
with every one — 31, 511, 10 — and so does the YAML 1.2 core schema.

The notation is not the value.  `0x1f` **is** 31: it compares equal, hashes
equal, and patches as 31.  What a number was written in rides as a presentation
tag beside `!bracket` and `!literal`, so the IR still holds only the integer.

```
0x1f vs 31     ->  k: !rmtag(hex) null      the notation
0x1f vs 0x20   ->  k: !replace              the number
                     from: 0x1f
                     to: 0x20
```

The output matrix, verified by running go-yaml over the YAML output:

| written | Tony | YAML | JSON |
| --- | --- | --- | --- |
| `0x1f` | `0x1f` | `0x1f` (31) | `31` |
| `0o644` | `0o644` | `0o644` (420) | `420` |
| `0b1010` | `0b1010` | `0b1010` (10) | `10` |
| `1e9` | `1e9` | `1e9` | `1e9` |

JSON drops the notation because JSON has no syntax for it, which works because
stage 0 made presentation a category — the tag never reaches
`writeTagIfPresent`, so there is no "cannot encode tags in json".

Two things came out differently from the plan:

- The tokenizer decides radix from the literal run it already computes for the
  string rules, so `numberStreaming`'s buffer-boundary handling is reused
  rather than duplicated.  Radix is tested *before* the string rules, since
  `0x1f` holds letters and would otherwise read as text.
- `parse` derives the notation from the token bytes, so no field had to be
  added to `Token` and no synthetic tag token is emitted into the stream.

`0644` stays an error, as does `0xzz` — the prefix says the run is a number, so
digits outside the base make it a botched one rather than text.  Integer keys
stay base-10 and a radix key is refused, since a key cannot carry a tag and the
notation would have nowhere to go.

## Why the YAML half is split

Reading `-I yaml` faithfully is not a numbers fix.  `o -I yaml view` agrees
with go-yaml on strings and nothing else: `0644`, `0x1f`, `08`, `1_000`,
`yes`/`no`/`on`, and `1:30` all read as strings where go-yaml gives 420, 31,
float64 8, 1000, bools, and 90.

And it is corrupting manifests today, which is worth its own issue rather than
a line in this one:

```
in    defaultMode: 0644     go-yaml: int 420
out   defaultMode: "0644"   go-yaml: string "0644"
```

The scope question — how much of YAML 1.1 to import, given `08` resolving to a
float is go-yaml being strange rather than a rule worth copying — is written up
in dfazjr7hh12krgy0e5n0.

The output side needs nothing new for it: `!oct` already writes `0o644`, which
is 420 to every reader.
