Design (agreed 2026-09-12)

This is not a compaction extension. Compaction's contract (docs/logd/compaction.md)
is that it removes the memory of how state was reached and never the state; a
current-state read stays exact across a compaction. Aging out log-like records is
a state change, so it is a separate RETENTION policy that issues ordinary delete
commits, plus one small true compaction extension so the deleted records leave
disk.

## 1. Retention: a system writer that issues delete commits

A rule names a container of log-like items, the field each item carries its own
timestamp in, and how old an item may be. Items are assumed to be log-like, so
requiring the timestamp field is reasonable and is what makes age exact: it does
not depend on the compaction policy, the snapshot cadence, or any new metadata.

    retention:
      every: 1h
      rules:
      - path: jobs.*
        match: {status: !or [done, canceled]}
        age: .updatedAt
        after: 1d
      - path: events{*}
        age: .at
        after: 1y

- `path`: the last segment is wild (`.*`, `{*}`, and `[*]` if arrays are taken;
  see open points) and names the items. Each item is deleted whole, never a
  field inside it. `..` is refused, as validateDataPath refuses it everywhere
  else: a fixed-depth pattern has pairwise disjoint matches, so items never nest,
  which "delete whole item" depends on.
- `match`: optional, the existing match language against the item. It tests
  structure and equality only; it has no ordering, which is why age is not
  expressed as a match operator.
- `age`: path inside the item to an RFC3339 timestamp (the format log entry
  timestamps already use). An item with no parseable timestamp there is kept and
  reported once per run, the same rule compaction applies to an unparseable
  record timestamp.
- `after`: duration. An item is expired when `now - age >= after` and `match`
  holds.
- `every`: how often the rules run. A timer, not the snapshot trigger: a quiet
  log never snapshots, so records would otherwise never expire.

Execution, per run: for each rule read the container (the server refuses a wild
read, so the writer reads the container and walks its children), evaluate age
and match per child, and commit `!delete` for the expired ones through the
normal session path, in batches of bounded size so a rule firing on a year of
backlog does not make one giant commit. Each delete carries a match precondition
on the item's timestamp field and matched fields (the CAS the patch protocol
already has), so a writer that touches the record between evaluation and delete
fails that item's delete and the next run re-evaluates it. Commits carry a system
author (the commit-author work that just landed), so watchers see the deletes as
authored deltas and history at an older commit still shows the record. The
schema still validates: a delete the schema forbids fails visibly rather than
corrupting a snapshot.

Baseline only. Scopes have deleteScope.

Nothing in storage changes for this part.

## 2. Compaction: `horizon`

A delete commit makes the record disappear from current state, but it survives
in every older root snapshot the tier policy keeps. Each tier keeps its eight
newest and tier count is unbounded, so some snapshot from every era survives
indefinitely. `compaction.horizon: 2y` means no history older than that
survives, regardless of tier. Current state is unaffected because SwitchDLog
writes a fresh baseline snapshot before every compaction. This is the piece
that actually frees disk, and it fits compaction's contract.

## Rejected

- Age from the item's last-write commit time: once compaction drops a record's
  delta past the cutoff the index has no last-write time for it, and with a 1h
  cutoff and a 1y limit that is exactly the records to expire. Keeping it would
  mean new per-item metadata that must survive compaction.
- Age witnessed by surviving snapshots (an item is at least N old if the newest
  surviving snapshot older than now-N holds it unchanged): derivable, but its
  precision is the tier spacing at that age (a 1y rule would fire between 1y and
  1.9y with the default policy) and it depends on snapshots being configured.
  Too hard to manage to be useful.
- A relative-time match operator (`!before 1y`): match has no ordering and is
  also the CAS precondition language, so a clock-dependent predicate would make
  preconditions non-repeatable.

## Open points

- Dense arrays `[*]`: deleting elements shifts indices under watchers. Either
  maps and sparse arrays only in v1, or arrays with deletes issued highest index
  first. Leaning to the former.
- Numeric epoch timestamps: RFC3339 only until a real producer needs otherwise.

## Carry into implementation

- The compaction section is not validated at config load today
  (server/fileconfig.go Validate), so a bad multiplier only fails at the first
  compaction. The retention section must be validated at load, and this is the
  moment to validate compaction there too.
- Docs: docs/logd/compaction.md ("what cannot be configured": no per-path
  policy) and docs/logd/index.md need the retention page and the horizon knob.
