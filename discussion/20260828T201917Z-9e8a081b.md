# the last case: a comment, not a marker

Seed 8, op 3, commit 4 -- the one case left after d536e71. The head and the read render
IDENTICALLY:

```
head: a: {} d: e: k2: nested: 2 k0: nested: 1
read: a: {} d: e: k2: nested: 2 k0: nested: 1
```

`nodeEqual` still says they differ, because it is `api.SameState`, which counts
comments -- and `encode.MustString` does not show them. Encoding with comments on:

```
head: a: {} d: e: # note 2 k2: nested: 2 k0: nested: 1
read: a: {} d: e:          k2: nested: 2 k0: nested: 1
```

Op 2 was `d.e <- # note 2`. The head keeps the comment; the replay through the
streaming processor does not.

So the last case is a comment lost on the READ path, which is a different thing from
everything before it -- those were the delta's shape, its markers, or where an
operation sat. This one is the processor's comment handling on a shape the lowering
produces and a client write does not: the comment arrives as a WRAPPER around a value
that is itself being introduced.

## also worth recording: two marker rules that did not work

Descending into a tagged container, so that `a.b <- !delete` marks a.b the way a
client's write does, looked right and measured worse: seed 8 unfixed and seed 14
newly broken, 1 -> 2. Reverted. So the marker rule that is in the tree -- descend
through untagged single-field containers, mark where the descent stops -- is not
obviously the last word, but it is the best measured.

## a note on the instrument

`nodeText` and `encode.MustString` do not print comments, so a probe built on them
shows two documents as identical when SameState says they differ. Every comparison in
this issue that was made by eye should be read with that in mind; the ones that
mattered were made with DeepEqualWithComments or SameState.
