## 10. `omitzero` is honored for `bool` fields ONLY — everywhere else it silently does nothing

`generator.go` consults `field.Omitzero` in exactly one branch of its kind switch:

```go
case reflect.Bool:
    if field.Omitzero {
        buf.WriteString(fmt.Sprintf("\tif s.%s {\n", field.Name))
        ...
```

`String`, `Int*`, `Uint*` and `Float*` are all emitted unconditionally. The reflection path
(`toIRReflectStruct`) reads only `field=` and never looks at the tag at all.

```go
//tony:schemagen=omit-probe,notag
type Probe struct {
    ID       string   `tony:"field=id"`
    Task     string   `tony:"field=task,omitzero"`
    Plain    string   `tony:"field=plain"`
    WithOmit []string `tony:"field=withOmit,omitzero"`
    NoOmit   []string `tony:"field=noOmit"`
}
```

generates

```go
irMap["task"]  = ir.FromString(s.Task)     // omitzero ignored
irMap["plain"] = ir.FromString(s.Plain)    // identical, as expected
if len(s.WithOmit) > 0 { ... }             // guarded
if len(s.NoOmit) > 0 { ... }               // ALSO guarded — no omitzero tag
```

**The slice guard is not `omitzero` doing its job.** It is unconditional for slices, maps and
pointers, which is what makes this hard to spot: those fields look like the tag is working. It
misled me for a whole stage — I concluded from the slice guards that codegen implemented
`omitzero` and the reflection path merely lagged behind it. It does not; both paths ignore it,
one of them just happens to guard collections anyway.

So `Probe{ID: "x"}` serializes as:

```
count: 0
id: x
plain: ""
task: ""
```

on BOTH paths, when the whole point of the tag was for `task`, `plain` and `count` to be absent.

Two consequences worth separating:

- **A documented tag is a no-op.** `omitzero` is parsed, stored on `FieldInfo`, covered by a
  test (`TestGenerateToTonyIRMethod_OmitzeroBool` — which tests the bool case, the one that
  works), and does nothing for the field kinds people mostly put it on.
- **A field with no `omitzero` is dropped when empty anyway** if it is a slice, map or pointer.
  That is the opposite failure: a caller who wants `items: []` on the wire — a meaningful
  "explicitly empty" — cannot get it, tag or no tag.

**Workaround in verse:** `codec/omitzero.go` prunes empty fields from the finished IR by walking
the Go value and the node together, ~100 lines. It treats an empty string/int/bool/slice/map/
pointer as absent, which is what the tag reads like it should mean.

**Suggested fix:** consult `field.Omitzero` in every branch of the kind switch, make the
collection guards conditional on it too, and honor the tag on the reflection path (which needs
the same emptiness test — the two paths producing different documents from the same tags is the
underlying hazard here, more than any individual field).

## 11. `omit`, `-` and `field=-` are ignored on the reflection path — a field marked for
exclusion is serialized

Same root as item 10 (the reflection path reads only `field=`), but the consequence is different
enough in kind to separate: this one puts data on the wire that was explicitly marked not to go
there.

```go
type Probe struct {
    ID     string `tony:"field=id"`
    Secret string `tony:"field=secret,omit"`
    Dashed string `tony:"-"`
    Named  string `tony:"field=-"`
}
```

`gomap.ToTony(&Probe{ID: "x", Secret: "shh", Dashed: "d", Named: "n"})` on v0.0.88:

```
Dashed: d
Named: n
id: x
secret: shh
```

All three exclusion spellings are ignored, and the two without a `field=` name are emitted under
their **Go** field names — so a private field appears on the wire under a name that was never
part of any schema.

Codegen gets `omit` right (`secret` is correctly absent there), so **the same struct tags produce
different documents depending on whether the type happened to be generated**. Whether a secret is
serialized should not depend on that.

`omit` is the one I would prioritize across everything in this issue. The rest cost readability
or a workaround; this one is the shape of a credential leak — a field named `apiKey` marked
`omit`, on a type that is not generated, reaching a log or an HTTP response.

**Workaround in verse:** none needed yet — no verse type relies on `omit`, precisely because I
found this before using it. That is luck, not design.
