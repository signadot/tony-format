Implemented in 4f5b1ea, named `commit` per the note above.

Correction to the issue text: the referenced `match_data.go` / `req.Meta.SeqID` HTTP handler does not exist at origin/main — there is no HTTP match handler or SeqID anywhere in system/logd. The real gap is that session `handleMatch` (session.go) unconditionally read at `GetCurrentCommit()`, with no commit field on `MatchRequest`.

What changed:
- api: `MatchRequest.Commit *int64` (field `commit`); regenerated api_gen.go + schema_gen.tony.
- logd: handleMatch reads at `Commit` when set, else current; rejects `commit < 0 || commit > current` with `commit_not_found` (a future commit would otherwise read as current, a negative one as empty).
- docd: single-route MATCH forwards the commit verbatim (no change needed); composed reads fan the SAME commit to base + every mount. This is coherent because base and logd-backed mounts share logd's single commit sequence (the same sequence the multi-mount tx machinery commits into).
- libctl: `MatchAt` / `MatchPatternAt` client helpers; `MatchParams.Commit` threaded to `Handler.Match`; reference logd-backed controller honors it.

Self-backed controllers (content not in logd): the Handler.Match doc now calls out that such a controller cannot honor a logd commit correctly — it can't coordinate a consistent point-in-time with the other controllers — so serving one risks a subtree out of sync with the composed document. Only safe when every write to that mount is isolated entirely to that mount; otherwise it should reject the historical read.

Tests: TestSession_MatchAtCommit (logd: historical vs current vs out-of-range) and TestDocd_ComposeAncestorReadAtCommit (end-to-end composed historical read across a logd-backed mount).
