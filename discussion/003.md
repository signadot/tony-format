Investigating the O_APPEND vs `dlf.position` question turned up a live corruption bug that
needs neither a panic nor a partial write. It is reproducible, and it produces exactly the
reported symptom.


`swapLogFile` (`compaction.go:294-309`) and `reopenLogFile` (`compaction.go:322-335`) install a
**fresh file handle** — offset 0 — and then set

```go
logFile.file = newFile
logFile.position = stat.Size()     // compaction.go:308, :333
```

**without seeking to the end.** `newDLogFile` did seek (`dlog.go:235`); the compaction paths never
did. Since appends used the shared file offset (`dlf.file.Write`), the first append after any
compaction swap wrote at **offset 0** — overwriting the head of the log — while returning
`currentPos = stat.Size()` as the entry's index position.

So after one compaction: new records silently overwrite the beginning of the file, and the index
records positions far past where anything was written. A later read at one of those positions
lands in whatever stale bytes still occupy that region — mid-record, so **the decoder reads a
frame header as document text**. That is the `\x00\x00\x2d\xd9` at offset 470.


`TestAppendAfterReopen_LandsAtReportedPosition` in the new
`system/logd/storage/internal/dlog/framing_test.go`. Against the old code:

```
framing_test.go:65: entry at pos1: commit = 2, want 1
framing_test.go:70: ReadEntryAt(pos2=78) error = position 78: reached EOF while reading length prefix
```

Entry 2 overwrote entry 1 at offset 0, and entry 2's recorded position was past EOF.


**B — the file offset is gone.** All writes now use `WriteAt` (pwrite) at an explicit offset;
reads already used `ReadAt`. `DLogFile.position` is the sole authority for the write frontier, so
there is no second source of truth to desynchronize. This fixes the swap/reopen bug by
construction, and it also means a failed append leaves `position` untouched so the next append
rewrites those bytes instead of appending after a stump. Touched `dlog.go:AppendEntry` and
`snapshot_writer.go` (`NewSnapshotWriter`, `Write`, `Seek`, `Close`).

`SnapshotWriter.Seek` is now a **virtual** cursor — it moves `logFile.position` only and never
seeks the shared fd. `snap.Builder` seeks backwards to patch its own header, and doing that on the
real descriptor relocated the append point for everyone else holding the file.

O_APPEND was rejected: it does not report the offset written to (which is the value the index
needs), and the snapshot blob-header patch (`snapshot_writer.go` `Close`, writing 4 bytes at
`headerPos+4`) is an in-place rewrite that O_APPEND would redirect to EOF. `os.File.WriteAt` also
refuses to operate on an O_APPEND file, so it would have foreclosed B.

**C — one write per record.** Header and payload are framed into a single buffer and written with
one call, in both `AppendEntry` and `SnapshotWriter.Close`. This removes the window where a length
prefix exists on disk without its payload. It is *not* crash atomicity — a single write can still
tear — which is why D is still required.

**D — torn-tail scan on open.** `newDLogFile` no longer trusts `stat.Size()`. `scanFrames`
(`dlog.go`) walks the framing from the start, mirroring `singleFileIter.next` including
`BlobHeaderMagic` blobs, and returns the offset just past the last frame that lies entirely within
the file. A shorter result means a torn tail: it is logged at Warn with the discarded byte range
and truncated. Both tear modes are caught — a partial prefix cannot be read, and a prefix whose
payload was cut short runs past EOF. A zero-length prefix is treated as unwritten space.

Covered by `TestOpenTruncatesTornTail` and `TestAppendPositionMatchesFileSize`.


`scanFrames` does **not** validate payload contents, so a frame boundary that happens to land on
plausible-looking garbage is still accepted. Per-record checksums are what make the scan decisive;
filed separately.

This also does not make anything durable. Records are still acked before fsync
(`hyda9h82h12krp8mcdn0`), so a crash can still lose acked entries — the tail is now *clean* rather
than *complete*. fsync-on-panic would narrow that window on the panic path specifically, but it is
not a durability mechanism (SIGKILL, OOM, power loss and `os.Exit` all bypass it) and if the panic
lands mid-record it just makes the torn record durable. Worth doing after this, not instead of it.


The `token/quoted.go` panics (`:207`, `:247`) are untouched and still real. Under this root cause
they are what turned a bad read into a dead daemon rather than a failed session — an availability
bug amplifying a corruption bug. The `QuotedToString`-must-not-panic work and the session-boundary
`recover()` both still stand.

Whether the tokenizer *also* has a mis-consumption bug is now unproven either way. The frame
misalignment is explained without it.
