Intended semantics (confirmed): a scope is a LIVE OVERLAY, not a frozen branch.
scope_read(commit) = full baseline state at commit, with the scope's own patches
merged on top. The merge handles hierarchy (no leaf-partitioning).

Expected results:
1. s1 writes a.x=5; later baseline a.x=99  -> scope reads a.x=5  (scope wins)
2. baseline a.x=1; s1 never writes a.x; baseline a.x=2 -> scope reads a.x=2 (ongoing baseline)
3. s1 writes a.x=5; later baseline a={y:9} -> scope reads a={x:5, y:9} (merge)
4. s1 writes a.x=5; later baseline a={x:99} -> scope reads a.x=5 (scope wins at its leaf)

Current bug: ReadStateAt applies baseline+scope patches interleaved in COMMIT order
(latest-commit-wins), so a later baseline write overrides a scope write (#1/#4 give
99). Same matchesScope logic feeds the watch, so a scoped watcher also gets the
baseline delta it shouldn't.

Read fix direction: baseline state first, then apply the scope's patches on top
(equivalently, separate baseline vs scope patches and apply baseline-then-scope).
Watch fix: a scoped watcher must not receive a baseline delta for a leaf the scope
has overridden (but non-overridden parts of an ancestor write still flow, per #3).

Open impl questions: (a) does logd snapshot/compact scope data separately (scope
snapshots) in a way that breaks "baseline-base + scope-patches-on-top"? (b) any
order-dependent patch ops (append/insert) where applying the scope's patches last
diverges from commit order?
