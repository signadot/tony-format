CORRECTING THE CORRECTION — comment #001 withdrew too much. The "retained entry becomes unreadable" claim is real; my audit there just never exercised a surviving PATCH, because with Cutoff 0 every baseline patch in the compacted file was dropped and only snapshots (which are indexed at the root only, so they have no below-root copies) survived.

Scope patches are retained regardless of cutoff (selectSurvivors: "Retain every scope patch until the scope is deleted"), so they give the case directly. One scope patch sharing a log file with baseline patches that the cutoff drops:

    before: scope patch commit=5 root B@1365 gen=0
    after:  scope patch commit=5 root B@1365 gen=0 -> B@0 gen=1 ; root read: ok
            deep kp="demo"          B@1365 gen=0 -> read interrupted by compaction
            deep kp="demo.x"        B@1365 gen=0 -> read interrupted by compaction
            deep kp="demo.x.scoped" B@1365 gen=0 -> read interrupted by compaction

The entry is retained and readable at its new position through the root segment. Its three below-root copies still point at the old position and old generation, permanently. A baseline patch inside the cutoff window behaves the same way — scope patches are just the easy way to construct it without faking timestamps.

So there are two mechanisms, not one:

1. Entries DROPPED by policy leave their below-root copies behind. Root-scoped consumers see the entry simply absent (history degraded to snapshot granularity, as designed); path-scoped consumers resolve the stale segment and get a hard ErrCompactionInterrupted. (This is what comment #001 measured, and it stands.)
2. Entries RETAINED but MOVED by the file rewrite have their root segment repositioned and their below-root copies left at the old position and generation. The data is right there and readable at the root; it is unreachable through the path index. (This is the original filing's claim. It stands. Comment #001 withdrew it in error.)

Both are permanent: ErrCompactionInterrupted documents "re-lookup the segment from the index and retry", and the re-lookup returns the same stale segment.

Confirmed impact:

    ReadPatchesInRange("demo.x.scoped", 0, cur, &scope)
      -> failed to read entry at B:0: read interrupted by compaction

And state reads were in this blast radius until 67220e2. readScopedStateAt took its scope patch range at the read's path; against the same compacted log:

    pre-67220e2 scoped read (scope range at kp): failed to read patch entry: read interrupted by compaction
    current scoped read:                         demo: x: hot: 6 scoped: "keep me"

Severity back to MEDIUM. Still fail-stop rather than silent corruption, still needs compaction enabled, but it is not confined to entries the policy meant to discard.

Fix note: updateIndexPositions/removeFromIndex can maintain the below-root copies without a full index walk — the entry's own patch node yields exactly the paths it was indexed at (the traversal indexPatchRec already does), so the old copies can be removed and re-added at the new position from the entry itself.
