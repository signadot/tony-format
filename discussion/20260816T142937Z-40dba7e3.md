Correction to the framing: this is not a safety issue. Every logd session is inside the trust
boundary, so a client which can store a !pipe already has whatever the daemon has, and running
a command as the daemon grants it nothing new. Scott's call, and it is right.

What survives is determinism, which is what the vocabulary excluded pipe FOR: "it calls out to
the system, so storing it means re-running it on every replay". Reading the same commit twice
returns two different documents:

    read 1 @2: stamp: 1786890553435891000
    read 2 @2: stamp: 1786890553438510000

A stored op which re-evaluates is not a value, and logd applies stored patches in three places
-- a full read, the stepped head, a watch's deltas. They stop agreeing: CheckHead reports a
divergence it attributes to the head, and a snapshot fixes one run's output into the base while
the log keeps replaying another, so the same commit means one thing before compaction and
another after. History stops being addressable, which is the property logd is for.

And the sharp case in this issue was never pipe. A client-supplied !arraydiff or !strdiff in the
patch BODY commits and then no read of the store succeeds again -- the same permanent loss as
7cdvym1fh12ksmd5g5n0, through a door the path-side check does not cover.

The fix is unchanged: hold a baseline write to the storage vocabulary, which is O(patch) and
reads no document. The wrinkle named below still needs settling first -- MergePatches
manufactures an !arraydiff for every [i] write path, so the vocabulary has to be applied to the
client's patch data before merging, or the baseline subset stated explicitly.
