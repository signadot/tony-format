Decided: no implicit raw. The fetched value is handed to f as an ordinary pattern, and a
document which happens to carry an operator tag is a case to meet if it ever turns up.

The premise holds: matchNode calls SplitChild(match) and never on doc, so a tag in a
document is never read as an operation. The only exposure is the crossing from doc side to
pattern side, which is what a get does and nothing else does.

Two things support leaving it alone beyond that.

!raw is positional BY DESIGN and says so: "Put !raw at the depth where literal comparison
starts; the enclosing pattern keeps ordinary match semantics." Making a fetched value raw
automatically is exactly the contagion the operator was written not to have.

And raw means MORE than "do not interpret the tags". As a match it "compares its subtree to
the doc as literal data: tags are compared, not evaluated, and the comparison is EXACT
rather than the partial object match of an ordinary pattern". So an implicit raw would
silently turn a fetched-object comparison from partial to total, which is a larger change
than the tag question that motivated it, and the wrong one to make by accident.

One caveat, recorded so nobody rests on a hatch that is not there: there is no spelling
today for "fetch, then compare the result as data". Composition is leftmost-outermost --
`!not.at(a.b) 3` negates the whole walk while `!at(a.b).not 3` asks at the landing node --
so `!raw.get-path a.b` reads as raw applied to the whole operator, comparing literally
against a node tagged !get-path whose value is the string "a.b". The user can put !raw
elsewhere in their own pattern, but not around this result.

So "let it be" means: accept pattern interpretation, and if a real document ever brings an
operator tag through a get, the answer is a spelling on the operator -- an arg beside
(root), most likely -- decided then rather than now.
