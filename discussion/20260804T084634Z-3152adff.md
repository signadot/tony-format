# Proposal: classify digit-leading scalars; carry notation as tags

Checked against `ae31b68`. All behavior below was run, not recalled.

## Cause

`token/tokenizer.go:600` dispatches on a leading digit straight into `numberStreaming`,
which consumes the maximal run of `[0-9.eE+-]` and hands the rest to the parser as a
separate token. There is no "is this a number?" decision, only "take the number-shaped
prefix" — hence the downstream `unseparated array elements` / `key not followed by :`.

The YAML branch of that same switch already does the right thing:
`tokenizer.go:601-621` scans the plain run, runs `number()` over it, and accepts a number
only when `numLen == off`, otherwise emitting a string. The fix for the tony branch is ten
lines above it in the same file.

This is not a round-trip break — `o -I yaml view` emits `cpu: "100m"`, quoted, and that
reparses. It is confined to hand-written tony, which is the audience `docs/motivation.md`
addresses.

## Rules

Scan the maximal literal run `R` at a digit (or `-` followed by a digit):

1. `number(R)` consumes all of `R` → **number**
2. `R` is all digits with a leading `0` → **error** (existing `ErrNumberLeadingZero`)
3. `R` contains a Unicode letter → **string**
4. `R` is `digits ('.' digits){2,}` → **string**
5. else → **error**, naming `R`

`number()` is extended in rule 1 to accept `0x/0X` hex, `0o/0O` octal, `0b/0B` binary
integers.

| input | today | proposed |
|---|---|---|
| `30s` `100m` `1Gi` `1h30m` `0m` `3d` | bogus parser error | string (3) |
| `1.2.3` `192.168.1.1` | bogus parser error | string (4) |
| `0x1f` `0o777` `0b1010` | bogus parser error | number 31 / 511 / 10 (1) |
| `1e9` `-2.5` `0.5` | number | number (1) |
| `0644` `007` | `leading zero` | `leading zero`, unchanged (2) |
| `1_000` `3..14` `1.` `1e+` | bogus parser error | *named* error (5) |

Rule 5's entire residue is malformed numbers, which stay loud. The cost of rule 3, stated
plainly: a typo that gains a letter (`replicas: 3l`) becomes a string rather than an error,
and the schema layer is what catches it. That is the price of the compromise and it is the
same price JSON and YAML pay.

## Radix literals are numbers, not errors

An earlier draft rejected `0x`/`0o`/`0b` to preserve loudness. That was wrong: nobody
writes `0x1f` meaning those four characters, so the format should mean 31. Rejecting it is
a format overruling an unambiguous intent, and it left tony with no way to write an octal
file mode at all.

This also matches what the ecosystem already does. go-yaml v3, run directly:

```
defaultMode  420          int      <- 0644
mask         31           int      <- 0x1f
b            10           int      <- 0b1010
o            511          int      <- 0o777
q            100m         string   <- 100m
d            30s          string   <- 30s
```

Every line of that agrees with the rules above except `0644`.

## Why bare leading zero stays an error

The same four bytes mean three different things:

- YAML 1.1 (go-yaml, under `sigs.k8s.io/yaml`, i.e. what kubectl reads with): `0644` = **420**
- YAML 1.2 core schema (`[-+]?[0-9]+` matches it as decimal): `0644` = **644**
- JSON: invalid

Any value tony picks is silently wrong against somebody's reader; erroring is the only
choice that cannot be. And it now has a fix to point at, which it did not before:
`0o644`, which is 420 everywhere including go-yaml.

Kubernetes' own docs concede the same point from the other side — they tell you to write
`420` because JSON has no octal notation.

## Interop bug found in passing

tony's YAML *input* path disagrees with go-yaml on exactly these tokens:

| | go-yaml v3 | `o -I yaml view` today |
|---|---|---|
| `defaultMode: 0644` | int 420 | string `"0644"` |
| `mask: 0x1f` | int 31 | string `"0x1f"` |
| `o: 0o777` | int 511 | string `"0o777"` |

So a real manifest read as YAML today produces a string where kubectl produces an int.
That is a live bug independent of this proposal, and this proposal resolves it: on YAML
input, honor YAML 1.1 (what the manifest means) and render it in tony as `0o644`, which is
unambiguous. The conversion becomes lossless *and* disambiguating.

Worth its own issue if this one gets long.

## Notation rides in tags, not the IR

The IR holds the value; notation is presentation and belongs where `!bracket` lives.
Verified, with no IR change required:

- `!bracket` is a tag the encoder consumes (`encode/encode.go:259,452,541`) and patch
  strips (`patch.go:194`). Bracket differences surface in diff as `!addtag(bracket)` — a
  presentation diff, not a value diff.
- A tag on a scalar integer already round-trips: `k: !hex 31` views back as `k: !hex 31`
  and diffs against `k: 31` as `k: !rmtag(hex) null`.

So: `!hex`, `!oct`, `!bin`, `!exp`. The lexer attaches one when it sees the notation, the
encoder renders from it, patch strips it, and `0x1f == 31` as values.

Canonical rendering, one form each, consistent with the normalization discipline in
`docs/tony.md`:

- `!hex` → lowercase prefix and digits: `0X1F` normalizes to `0x1f`
- `!oct` → `0o644`
- `!bin` → `0b1010`
- `!exp` → normalized scientific, mantissa in [1,10): `1.50e3` normalizes to `1.5e3`,
  `1e+9` to `1e9`

Open detail: zero padding. `0x00ff` as a mask carries visual meaning that canonical
`0xff` drops. Tag arguments already exist (`docs/tony.md` §Tag Arguments), so `!hex(4)`
could carry a width. Recommend shipping without it and adding it only if the loss is felt.

## Pre-existing wart the same principle exposes

Notation is *already* in the IR and already misbehaving. `ir.Node.Number` holds raw source
text and `ir/node.go:415` compares it textually, while the encoder renders canonically:

```
k: 1.0   vs   k: 1     ->  k: !replace
                             from: 1
                             to: 1
k: 1e2   vs   k: 100   ->  same
```

`o view` on `k: 1e2` prints `k: 100`, so that diff asserts a value change between two
things that render identically. It is a lying diff, present today with no radix work
involved.

The fix is the same principle: numeric equality should be numeric, not textual, and
anything presentational should be a tag. Then `1.0 == 1`, `1e2 == 100`, `0x1f == 31` all
fall out and the phantom replace goes away. Separable commit — its own diff-golden fallout.

**Precision hazard to settle there:** canonical text must not route through float64.
`1e400` has no float64 and a 401-digit decimal expansion, and the comment at
`token/numbers.go:5` already flags large integers like `10000000005`. Comparing numerically
without materializing a decimal expansion is the thing to get right.

## Staging

1. **Named lexer error** (rule 5's message). Required whichever way the language question
   goes — this is the issue's own floor. Standalone, no spec change.
2. **Rules 3 and 4** — the k8s surface: `100m`, `1Gi`, `30s`, `1.2.3`. Encoder mirror in
   `NeedsQuote` (`token/quoted.go:39`); `TestNeedsQuoteAgreesWithRoundTrip` enforces it.
3. **Radix literals + notation tags** `!hex` `!oct` `!bin` `!exp`, plus the YAML-input fix.
4. **Numeric equality** in the IR.

## Spec changes

- `docs/tony.md:89` "may not start with a digit" becomes the rule-1-through-5
  classification, with a new §Numbers stating it.
- `docs/tony.md:55` "exactly 1 degree of freedom" — bracketing is joined by integer/float
  notation. Both are tags, so the sentence can be recast as *presentation tags are the
  degrees of freedom* rather than enumerating them.

## Fallout to expect

Rule 3 makes `100m` a legal literal, so `NeedsQuote` stops quoting it and stored output
changes `cpu: "100m"` to `cpu: 100m`. Textual churn only — no semantic change — but it is
visible in every golden file that came through the YAML reader.

`KPathQuoteField` (`token/quoted.go:69`) is built on `NeedsQuote`, so path fields unquote
too (`.100m`). kpath indices are bracketed so there is likely no ambiguity, but it needs a
test; giving kpath its own predicate is the cheap out if it bites.
