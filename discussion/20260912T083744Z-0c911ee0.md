Dense arrays: resolved (2026-09-12)

The open point on dense arrays closes as: a rule over an UNKEYED dense array is
refused at config load. Items may be the children of an object (`.*`), of a sparse
array (`{*}`), or of a keyed array; never positions in a dense one.

Why. A dense index names a position, not an element (docs/logd/writes.md, "An array
index must name an element"). The retention writer reads the array, decides
`events[3]` is expired, and commits a delete at `events[3]`; a concurrent insert or
delete before that index, between evaluation and commit, leaves an element at
position 3 and makes it a different one. The commit-time check only asks whether an
element is still there, not whether it is the same one. The CAS match narrows the
damage to a neighbour whose timestamp and matched fields are identical -- duplicate
events -- which is rare, and the design would be resting on "rare". On the read
side, every expiry shifts every later index, so a positional watch on `events[7]`
silently watches a different element after each run, on every tick for as long as
the rule exists. Batching several deletes into one commit is NOT the problem:
`!arraydiff` positions are simultaneous against the shared sequence.

logd's own answer already exists: docs/logd/keyed.md says that for anything durable
where two writers may touch the array, the identity belongs in the schema and writes
name elements by key. Retention is a second writer by construction. A keyed element
has a path of its own, `events(WIDGET)`, and does not move when a sibling goes.

So: refuse the unkeyed dense array at load, with a message that says to declare the
array keyed with `!logd-key` or `!logd-auto-id`. Items must be objects anyway, since
they carry a timestamp, and auto-id generates the key for a producer that has none.

Cost. kpath has no wild keyed segment today, and `[*]` deliberately does not match a
keyed element (ir/kpath/segment.go, issue 61766xadh). Add a `(*)` segment so a rule
over a keyed array is written `events(*)`, keeps the item kind visible in the rule,
and can be checked against the schema at load like the other kinds.
