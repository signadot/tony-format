# proposal: !comment carries an optional child

Tag arguments cannot hold spaces, so the positions stay in the operand. Add a third
field to it:

```
!comment {
  head:  ["# a", "# b"]      # optional, as today
  line:  ["# latch"]         # optional, as today
  child: <patch or match>    # NEW, optional
}
```

- `child:` absent -- exactly today's behaviour, the comment is stated and the value is
  untouched.
- `child:` present -- it is applied to the value, and the comment is then stated on the
  RESULT. That order, because the comment describes what the value has become.
- In a match, `child:` is the match applied to the value, so the operator stays
  match-and-patch as it is now.

Absence of the field is not `child: null`. A missing `child:` says nothing about the
value; `child: null` is a patch of null and sets it. Same distinction the store already
turns on, and worth stating rather than discovering.

Compatibility: existing documents keep working, since the field is optional. Old
READERS reject the new form -- `Instance` refuses any field but head/line -- so a log
written by a newer logd is unreadable by an older one. Accepted.

## what it costs, which is the real content

Every structural walker over patches has to learn that `child:` is a transparent level
and that `head:`/`line:` are not paths. Today they learn nothing: they descend into an
operand as if it were data. Measured -- a write of `{a: !comment {head: ["# note"]}}`
indexes

```
index paths: [ "" a a.head a.head[0] ]
```

`a.head` and `a.head[0]` are not paths in the document. Harmless enough today (spurious
entries at paths nothing reads), and NOT harmless with a child: a change at `a.e` would
index as `a.child.e`, and a narrow read of `a.e` would miss the entry that carries it.

The walkers: `indexPatchRec`, `api.validateForStorage`, `api.NeedsLowering`,
`server.patchMayAffect`, `markDeltaRoots`, `annotateKeyed`, `mergeop.FindUnsafe`, and
the streaming processor's patch walk.

## so the proposal is really two things

1. the field, as above;
2. a shared answer to "which parts of an operand are document paths", so the walkers
   stop guessing.

`mergeop.SplitChild` already identifies an operation and its operand. A companion --
say `mergeop.OperandPaths(n)`, answering the descendants that are document paths and
at what path each sits -- would let all eight walkers ask one question instead of
carrying eight copies of the answer. `!comment`'s `child:` is then one entry in that
table rather than eight special cases, `!raw` is another (they already stop there, each
in its own way), and the `a.head` wrongness above is fixed by the same stroke.

Doing (1) without (2) is what makes it expensive; doing (2) first makes (1) small.
