## not a defect -- the reproductions were ambiguous, and wrongly read

Both examples put the comment above a FIRST field, which is the CONTAINER's comment
position and not the field's. The container kept its comment, which is correct. What I
read as the comment migrating was the container's own comment being rendered above
whatever field now comes first.

Placed where it unambiguously belongs to the value being deleted, it goes with it:

```
doc     x: 0 / a: 1 / b: 2
patch   x: 0 / # about a / a: !delete null
result  b: 2 / x: 0                              comment gone, correctly

doc     d: {z: 0, e: 1, k: 9}
patch   d: {z: 0, # new, e: !delete 1}
result  d: {k: 9, z: 0}                          comment gone, correctly
```

The irony is that this is the same ambiguity 7c4e04c fixed on the ENCODER side earlier
today -- the line above a container's first entry means the container -- and I did not
apply it to my own test.

Closing as invalid. Nothing to fix.

## what survives

The composition note, which was never part of the claimed defect: `!comment.replace`
fails with `comment op position is "head" or "line", got "from"`, because the head of a
composed chain takes the child and `!comment` validates the child's field names
strictly. It is not a general rule about composing child-taking operations --
`!replace.strdiff {from,to}` composes and answers correctly.

So if a single node ever needs to state both a comment and a value change --
which is what xqpvk3ehh12ks89mj5n0 wants -- `!comment` taking its positions as tag
ARGUMENTS would make it compose with anything. That is a live design question and
belongs on that issue, not here.
