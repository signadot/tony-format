Found and fixed in 55e47c1.

getSingleLiteral counts brackets and refuses the literal if any are open at the end of its scan — but it cannot tell "stopped at a space with { open" (a bad literal) from "ran off the end of the buffer with { open" (unfinished; the } is in the next read):

    getSingleLiteralStreaming("abc")      -> EOF                        needs more data
    getSingleLiteralStreaming("abc{def")  -> bad literal: unbalanced {}  and the } is coming

So any literal holding a { or a [ killed the session when a read boundary fell between the bracket and its closer. The truncated-rune case was already handled this way; the brackets were not.

The constant column is because the error is reported at the LITERAL's start, not where the scan stopped: a value beginning 4084 bytes into a wire document, with the 4096 boundary landing inside it. Offsets differ per document, that column cannot. `...?...` is Pos.String with neither context nor document — every streaming error looks like that.

Repro at the session's own path (stream.TestBracketAcrossAReadBoundary): wire-encode a value holding a bracket, read it over a chunked reader, walk the bracket across 4096.
