Added an end-to-end walkthrough to the plan (dcfcb5c): go-tony/docs/tag-namespacing-plan.md, section "What it looks like when both are done".

It runs two consumers who both chose the prefix "ext" through the whole path -- defining an operation, publishing a context under a URI, a document binding a prefix to that URI, applying it, and an unbound prefix. Marked as a sketch: only mergeop.RegisterNamespaced exists today, and the rest is written out so the shape can be rejected cheaply rather than discovered halfway through C.

Two things it makes concrete that this issue only named.

The payoff is legible in code. Two Tools each register "shout"; neither sees the other's; a document bound to acme's URI gets acme's operation whichever library is also linked in. Today the second Register fails or silently loses, depending on init order -- which is not a hypothetical, since the namespace tests in mergeop leak into the summary-coverage test for exactly that reason.

The open decision becomes visible where it bites. In the walkthrough a document carries

    context: {ext: "acme.example/tony/ops"}
    patch:
      greeting: !ext:shout "hi"

which is a shape logd would have to store and hand back. A stored patch holding !ext:shout means nothing to a reader without the binding, so either the binding is stored beside it or the store refuses the write. That is step 2 of the walkthrough rather than a bullet at the end, and it is still the thing to settle before D1 is written.

The tony in it parses and the `o` examples were run against the current build.
