Fixed in e74bb7b.

It was the BALANCER, which turns block form into brackets before the parser sees
anything. Balancing your example gives

    [ { name : a  # about rule b }  { name : b } ]

-- the comment is consumed while looking for the next KEY of the element before
it, so it ends up inside that element's braces. There it precedes no field, and
an object has nowhere to hang a comment that heads nothing, so parseObj drops it.
That is why it was on no node at any depth rather than misplaced.

A comment belongs to what follows it, so when what follows ENDS the object being
balanced -- the next element of the enclosing array, or an outdent -- it is left
for the caller, and lands between the two elements:

    [ { name : a }  # about rule b  { name : b } ]

Head comments only. A line comment trails the value before it wherever that value
sits, and applying the same rule to those moved line comments off their values
(caught by the stream round-trip test).

The encoder also writes an element's head comment above the "- " rather than
after it, so

    - name: a
      stage: open
    # about rule b
    - name: b
      stage: open

goes out as it came in, byte for byte. Note that `- # about rule b` and the above
are the SAME IR, so only one of them can round trip; this is the one people
write, and the one your report calls natural.

Checked: between two objects, before the first element, several comments in a
run, nested lists, scalar elements, and the round trip for all of them.

Keeping the comment also uncovered something next door: ListKPath handed back the
comment wrapper while GetKPath answered with the value, so the same path gave a
different node depending on which you asked. Both answer with the value now, and
WithComments keeps the wrapper -- which is what ListKPathWith already said it
did.
