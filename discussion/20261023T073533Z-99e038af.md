Assessment and a proposal, from reading `storage/compaction.go`, `scope_compaction.go`, `index/footprint.go`, `index/cover.go`, `replay_floor.go` and `lower.go`.

## The store already has the mechanism, for scopes

What the issue wants — "a later write of this record retires the earlier one" — is what scope compaction does today. A stored write is **absolute** (`lower.go`, and this holds for baseline as well as scopes, deliberately), so a later statement at or above a path that covers it *dominates* the earlier one (`index.Cover`), and a dominated statement contributes nothing to any fold from the dominating one on. The footprint keeps, per scope, the statements no later statement dominates; an entry beyond the cutoff with no live statement is dropped. A scope that rewrote one field a thousand times keeps one entry.

Baseline gets none of this, by design: a baseline entry is kept or dropped by its time alone (`selectSurvivors`), because its history is promised exact within the cutoff. That promise is the only thing standing between verse's outbox record and the scope treatment.

## The constraint the candidates have to meet

The replay floor and the baseline floor are **one number for the store** (`replay_floor.go`). Any dropped baseline patch raises them to its commit: every watch resuming from below it is told `replay_compacted`, and every read below it is answered at a snapshot's commit. So "drop this path's overwrites after an hour" cannot mean "drop them and raise the floor" — on this store the floor would sit minutes behind the head and every reconnecting watcher would re-initialize, which defeats the whole store to save one path.

A per-path history therefore has to drop records **without moving the floors**, and that is a contract change, not a knob: at such a path, the store stops promising exact history.

## Proposal: a schema annotation, `!logd-current`

Declare it in the schema, beside `!logd-key` and `!logd-auto-id`, on the field whose value is a current reading and nothing more:

```tony
define:
  iod:
    name: string
    out: !logd-current {delivered: int, failed: int, lastPass: string, lastError: string}
```

Of the three candidates this is the right one because the fact is the **writer's**, about the **data**, and is stated **once**: verse knows `out` has no history worth keeping; a config pattern would make an operator say it, in a file versioned apart from the data, per store; a write option would be repeated on every write and one writer that forgot it would silently keep history for everyone. A type annotation covers every path of that shape (every iod's `out`) at once, which a path pattern does not do cleanly. And the schema is already how the store learns what it may not infer from the bytes — keying — so the consumer, parse and rebuild paths exist.

What it means, stated as the contract at a declared path:

- **The current value is exact, always**, as it is everywhere.
- **No history is kept past the current value.** Compaction drops an entry when every path it states is a declared path, and each is dominated by a later statement — `Cover` as it stands: a total cover at or above, a whole cover above, a whole cover at the path when the entry needed only whole. Age does not enter: dominated is dominated inside the cutoff too (the active log is never compacted, so the record of the last few minutes is there regardless).
- **The floors do not move** for such a drop.
- **A read at a past commit** is exact at every path but a declared one, where it answers the newest surviving statement at or before that commit — a value the path held, at some commit at or before the one asked for. The `commit` the read reports stays the one asked for, because the inexactness is declared on the path, not discovered on the commit. (This is the tension with `AnsweredCommit`'s "a property of the commit, not of a path"; the annotation is where it is resolved, by the writer giving up the exactness that rule protects.)
- **A watch replay** across a dropped entry delivers the dominating statement, which is the path's state; the watcher lands where it would have and misses an intermediate value nobody wanted. A replay always runs to the head, so the dominating statement is always in range.
- **Preconditions** read at the head and are unaffected. Retention reads items at the head too.
- **A mixed entry** — a transaction that stated a declared path and an undeclared one in one commit — is kept whole for the undeclared path's sake. Nothing is rewritten inside an entry.
- **A partial overwrite** dominates only what it restates: `{lastPass: t}` retires the earlier `lastPass` and nothing else, so an entry stays until every field it stated has been restated. Verse writes the whole record each pass, so for its records every pass dominates the last.

How compaction decides it, two options:

1. **Baseline footprint.** Track live statements at declared paths exactly as the footprint does for a scope (a pseudo-scope for baseline, holding only declared paths, so it stays small). Dominance decided at the write; compaction's pass is a lookup. Needs the declared set at index time and on rebuild, which the schema commits in the log give, as keying does.
2. **Decide in the walk.** Compaction already walks the inactive file once and reads each entry; keep the newest statement per declared leaf as it goes, and drop an earlier entry when a later one in the same file dominates all of it. A dominating write in the *other* log is not seen, so the last statement per leaf per file survives one round and goes the round after. No index change, no footprint; the lag is one record per leaf per file.

I'd start with 2: it is the narrow rule, and it is confined to `compaction.go`. 1 is what to grow into if the walk's tracking ever has to be more than a small map.

## Not proposed now

- **A per-path duration** (`!logd-current 1h`). The same mechanism supports it — the dominated check gated by the path's own cutoff — but no path in the table wants it; every one is "no history". Add it when a consumer appears.
- **A config path pattern.** See above: the fact is the writer's.

## What it does and does not fix on staging

With the five paths in the table declared, each compaction would drop nearly the whole inactive log instead of 1.5% of it, so the rewrite shrinks from ~620 MB to the record set that is not an overwrite. It does **not** change the snapshot cadence (one every ~1,200 commits, driven by `maxCommits`) or the 25 minutes each snapshot takes, which is m56xswgsh12ks9ravdn0's question and stands on its own. Verse writing only on change is still right, and orthogonal: a schedule's tick changes every minute by nature.
