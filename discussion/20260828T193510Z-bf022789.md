# the snapshot class: narrowed to marker DEPTH, four hypotheses eliminated

## the disagreement, concretely

Replaying a failing seed and stopping at the first commit where the two appliers
disagree:

```
stored:  a: b: c: k1: nested: 8   k1: 15   k2: 14
head:    ... a.b.k1 = 15
replay:  ... a.b.k1 = 11
```

The stored delta ASSERTS `a.b.k1 = 15`. The head has 15. The replay has the value from
before the write. So the replay is not applying part of the entry -- and every
difference seen has this shape, a stale or missing value rather than a wrong one.

## eliminated, each by measurement

**!insert's semantics.** Put back to merging: 24, unchanged. Not it.

**absoluteInserts, the post-pass that strips !insert off an introduced object.**
Disabled: 24, unchanged. Not it.

**Absoluteness as such.** Turning DiffAbsolute off gave 0 -- and that reading was
WRONG: a non-absolute delta carries !replace, ValidateForStorage refuses it, and every
write fails. 131 other tests fail in that configuration. The 0 meant no snapshot check
ever ran. Recorded because it is exactly the kind of green that means nothing.

**Marker COUNT.** markDeltaRoots descends into every branch, so one entry carries
several markers where the client's patch carries one per participant. Marking a single
root at the shallowest node covering all changes -- one marker, still not the document
root -- gives 24. Unchanged. Not it.

**A marker at a path the base lacks.** Marking only as deep as the base at commit-1
actually goes: 24, unchanged. The base does have those paths.

## what is left

Marker DEPTH, and only against a snapshot. Marking the document root gives 14 rather
than 24; one marker at the branch point gives 24; markers at every leaf give 24. So it
is not how many, it is how deep -- and it only bites once a snapshot is the base, since
nine single-write shapes and six multi-write sequences across a snapshot boundary all
agree (write, snapshot, write; repeated leaf; add/delete/add; branch deleted and
rebuilt; two branches interleaved).

The next thing to check is the SNAPSHOT'S OWN INDEX, which is deliberately size-bound
-- storage/CLAUDE.md: "The index doesn't record every path, only significant
checkpoints (size-bound). Reads may require scanning events from an ancestor path." A
marker deeper than any checkpoint may be a patch the replay cannot place. That would
explain depth mattering, count not mattering, and the whole thing being invisible until
a snapshot exists.

Root marking is not the fix even so: it is what made every narrow read replay every
write, 125us -> 17ms after a thousand writes elsewhere.
