# Completeness audit of the plan above

Checked the plan against the code. It was not complete — one hard blocker, several
missing edit sites, and one claim in the previous comment that is wrong.

## Correction: the phantom diff is not textual

The previous comment said `ir.Node.Number` holds raw source text and `ir/node.go:415`
compares it textually. That is wrong. The parse path never sets `Number`:

- `ir.FromInt` sets `Int64` (`ir/node.go:114`), `ir.FromFloat` sets `Float64`
  (`ir/node.go:122`)
- `Number` is only the `json.Number` fallback, and every consumer checks `Int64`/`Float64`
  first: `ir/hash.go:45-53`, `ir/compare.go:72-86`, `match.go:130-138`,
  `mergeop/raw.go:124-130`

So `1.0` vs `1` is unequal because a float node is not an int node — which is defensible,
not a bug.

The actual defect is in the **encoder**, and it is worse than a lying diff:

```
$ cat n1.tony            ->  k: 1.0
$ o view n1.tony         ->  k: 1
$ o diff n1.tony <that>  ->  k: !replace
                                from: 1
                                to: 1
```

The document is not equal to itself after a round trip. Encoding is not injective on
integral floats — `1.0` is emitted as `1`, which reads back as an integer.

That is a real bug but it is **not this issue**, and it is not a prerequisite. Stage 4
("numeric equality in the IR") should be dropped from this plan; the encoder round-trip
bug wants its own issue.

## Blocker: JSON output errors on tags

```
$ o -O json view <doc with k: !hex 31>
error encoding result 0: encode error: cannot encode tags in json
```

Any document containing a radix literal would fail `-O json` outright. `!bracket` escapes
this only because `encode/encode.go:237-238` strips `!bracket` and `!literal` before the
check — verified a bracket-only document encodes to JSON fine.

Notation tags must join that strip, and JSON must render the decimal value.

## YAML output leaks the tag

```
$ o -O yaml view <doc with k: !hex 31>   ->  k: !hex 31
```

It should emit `0x1f`, which go-yaml reads back as 31. So there is an output matrix the
plan never stated:

| | tony | yaml | json |
|---|---|---|---|
| `!hex` 31 | `0x1f` | `0x1f` | `31` |
| `!oct` 420 | `0o644` | `0o644` | `420` |
| `!exp` 1e9 | `1e9` | `1e9` | `1000000000` |

## Presentation tags are ad-hoc string literals at five sites

`!bracket` is matched by hand at `patch.go:194`, `patch.go:231`, `mergeop/raw.go:149`,
`encode/encode.go:237`, and `!literal` at `encode/encode.go:238` — so there are already
two presentation tags and no shared notion of the category.

Adding four more to that scheme means five-plus sites each, and a miss is silent: a
notation tag that leaks into a diff shows up as a spurious `!addtag(hex)`, and one that
leaks into JSON is the hard error above. This wants `ir.IsPresentation` /
`ir.StripPresentation` first, with `!bracket` and `!literal` moved onto it.

## parse.go: three base-10 integer parses

All would reject radix literals:

- `parse/parse.go:250` — `strconv.ParseInt(..., 10, 64)`, scalar value
- `parse/parse.go:449` — same, value in the other arm
- `parse/parse.go:627` — `strconv.ParseUint(..., 10, 64)`, integer map key

## Keys cannot carry a notation tag

`docs/tony.md:497` — tags may not be placed on a key. `docs/tony.md:426` — integer map
keys are base-10. So `0x1f: v` has nowhere to put `!hex`.

Needs a decision, not an implementation: reject radix notation in key position, or accept
it and silently canonicalize to decimal. Reject looks right — it keeps sparse-array keys
exactly as specified.

## Negative radix

`tokenizer.go:502` handles `-` followed by a digit as its own path into the number
scanner. `-0x1f` needs the same classification, and it is a separate edit from the
digit-leading branch at `tokenizer.go:600`.

## Stage ordering has a hidden dependency

Radix literals must land in `Int64` at parse time — they cannot lean on a later
canonicalization step, since gomap (`gomap/from.go:304,376,453`), schema, and hash all read
`Int64`/`Float64` directly. Good news: that means once parse is right, those three need no
changes at all.

## NeedsQuote is the inverse of the whole classification

`token/quoted.go:39` currently returns true for every digit-leading string. Afterwards it
has to encode the full rule set: `"100m"` no longer needs quoting, but `"0x1f"`, `"007"`,
`"1.2"`, `"1e9"` and `"1.2.3"` all still do, each for a different reason.
`TestNeedsQuoteAgreesWithRoundTrip` is the check, and it should be extended with the table
from the previous comment before the lexer changes, so it fails first.

## Open: how the tag gets attached

`TTag` is a token type (`token/types.go:23`, consumed at `parse/parse.go:504,672`), so the
tokenizer could synthesize a tag token ahead of the number. That raises position and
comment-association questions for a token with no source text.

The alternative is a notation field on the number `Token` that `parse` turns into a tag
when it builds the node. That keeps synthetic tokens out of the stream and puts the tag
construction next to the `ParseInt` calls that have to change anyway. Recommend this one.

## Revised staging

0. **`ir.IsPresentation` / `ir.StripPresentation`**, with `!bracket` and `!literal` moved
   onto it. Pure refactor, no behavior change, unblocks stage 3.
1. **Named lexer error** (rule 5). Unchanged — standalone, no spec change.
2. **Rules 3 and 4** (`100m`, `1Gi`, `30s`, `1.2.3`) + `NeedsQuote` inverse + the
   round-trip table.
3. **Radix literals + notation tags**: tokenizer digit branch *and* `-` branch, notation on
   the Token, three `parse.go` parse sites, key-position rejection, the JSON/YAML/tony
   output matrix, and the YAML-input fix.

Dropped: the old stage 4. Split out as its own issue — encoding is not injective on
integral floats.
