## 12. `omitzero` on a STRUCT-valued field is still ignored by codegen

The scalar and collection cases are fixed. A struct-valued field is not:

```go
//tony:schemagen=verse-config,notag
type Config struct {
    Addr   string       `tony:"field=addr,omitzero"`
    Format FormatConfig `tony:"field=format,omitzero"`
    LLM    LLMConfig    `tony:"field=llm,omitzero"`
}
```

`Config{Addr: "x"}`:

```
reflection          generated
addr: x             addr: x
                    format: {}
                    llm: {}
```

The generated code emits the nested call unconditionally:

```go
// Field: Format
node, err = s.Format.ToTonyIR()
if err != nil { ... }
irMap["format"] = node
```

whereas the pointer-to-struct branch right beside it already does the right thing with
`if s.Field != nil`. So it is the value-struct branch specifically that needs the guard — an
`isZeroValue`-style check, or delegating to whatever the scalar branches now use.

**This is what is keeping verse off codegen**, and it is a narrow gap: exactly five fields in
the whole codebase have this shape (`Config.Format`, `Config.LLM`, `Gate.Match`,
`Condition.Subject`, `ResourcePred.Kind`). `Gate.Match` is the one that matters — an empty
`match: {}` on every default gate, in a document people author and read by hand.

Nothing else blocks adoption: everything I generated compiled and round-tripped correctly.

## 13. The blank-field schema marker is silently ignored by codegen

`gomap`'s runtime reader (`GetStructSchema`) accepts the marker on an anonymous field, and its
own doc comment documents that form:

```go
type Config struct {
    _    struct{}  `tony:"schemagen=verse-config,notag"`
    Addr string    `tony:"field=addr,omitzero"`
}
```

`tony-codegen -dir .` on that package prints `Processing package: config`, **exits 0, and writes
nothing at all** — no Go file, no schema, no diagnostic. Converting the identical marker to the
`//tony:schemagen=` doc-comment form generates correctly.

So the two readers disagree about how a type declares its schema, and the codegen side fails
silently. Either accepting the blank-field form or rejecting it with a diagnostic would be fine;
succeeding-while-doing-nothing is the bad case, because the package simply appears to have no
annotated types.

(This is how verse's config package sat "annotated" for a while without anyone noticing nothing
was generated.)

## 14. A type ALIAS cannot be resolved across a package boundary

```go
// package codec
type Format = format.Format   // re-exported so callers need one import

// package config
type FormatConfig struct {
    Default *codec.Format `tony:"field=default,omitzero"`
}
```

```
failed to resolve type for field "FormatConfig"."Default":
failed to find type "Format" in package ".../verse/codec": "Format" is not a named type
```

Re-exporting a type by alias is an ordinary Go idiom, and the alias IS the aliased type, so the
resolver could follow it. Worked around by spelling the field `*format.Format` — identical type,
different name — but the error is only actionable if you happen to know the field's declared
type is an alias.

Worth noting the diagnostic itself is good: it names the field, the package and the reason. The
item-3 diagnostics generally are a big improvement — the one for an unannotated referenced type
even suggests `codec=custom`, which is exactly the right hint.
