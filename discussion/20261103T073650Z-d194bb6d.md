## Should strict become the default? A survey of the four consumers

The deferred question, taken up now. Four things would feel a change of default: this repo, the signadot repo's `sandboxes/deploy/{operator,charts}` builds, and verse. Each was inventoried for every `$[…]`/`.[…]` it holds, which names those reference, whether the env always binds them, and whether any expression leans on `??`, `?.`, `in`, a ternary or `fail()` to cope with absence.

**Recommendation: make strict the default, in the plain-path form proposed above.** An expression that is only names, `.field` steps and constant indexes is walked strictly against the env, and an absent name, field or index is an error naming the segment. Anything else (`??`, `?.`, `in`, a ternary, a call, a comparison) evaluates as today. No AST rewrite, no typed env, so the `nosuch ?? "d"` wrinkle and the Strict review findings do not come back. A per-reference opt-out already exists in the language, `a?.b` is null when `b` is absent, so no Lenient option is needed.

### What the survey found

**This repo.** No shipped file breaks. Every example `build.tony` defaults every name its patches use. `mergeop/let` already refuses an unbound name itself, added after a misspelt `.[nope]` expanded to null and, as a match, matched every document (`TestLetRefusesABindingItCannotEvaluate`). That is the clearest evidence leniency bites. What changes: the first row of `TestWhatAnAbsentPathAnswers`, the "a missing b on a present a is null" sentence in `docs/eval.md`, `docs/build-eval.md` and `eval/doc.go`, and a hand-run `o eval` whose `-e` is missing errors instead of writing `null`. A `dirbuild` `if:` whose name is missing currently applies the patch, since only a boolean false skips (`dirbuild/dir.go`); strict turns that into an error.

**signadot operator and charts.** Nothing breaks. Every referenced name has a `build.env` default or is always passed by the Makefile. No `??`, `?.`, ternary or `fail()` anywhere. The one bare name is `chartVersion` in the chart's `Chart.yaml`, absent only on a hand run, where it renders `version: "null"` today; strict is the fix there. The one `in` is inside a `filter` over a list, not a plain path, so it is untouched.

**verse.** Nothing checked in breaks. Verse calls `ExpandString` once, for a gate `pose`, with `subject.name` and `subject.value`. No checked-in charter uses `pose`, every `!let` name is bound, and none reads a field. The only behaviour change is a pose naming a payload field the subject lacks: today it renders "null", under strict the pose is dropped, a problem is recorded on the rule and the question falls back to `reason`, which verse's gates doc already describes. That matches verse's own error-on-absent rule for its `$subject` derefs. Verse's pose design doc documents the null rendering and advises `?? "…"`, which keeps working under plain-path strict. Its proposal to move charters onto `$[…]`/`.[…]` wants error-on-absent and gets it by default.

### What plain-path strict does not catch

An absent name inside a larger expression: `$[a.nope == "x"]` is silently false, as it is today, and `$[nosuch == "x"]` likewise. Worth a sentence in the docs rather than a wider rule.

### Cost

Here: the shape check plus a strict env walk in `eval`, one test row, three doc sentences, a release. Operator and charts: a go-tony bump only. Verse: a bump and an edit to its pose design table.
