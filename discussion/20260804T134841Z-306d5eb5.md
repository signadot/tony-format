# Both open risks settled; the plan gets simpler and one detail gets sharper

Scope is set aside per the client's needs and filed as 9b2vpggxh12ks0qde5n0.  So
this is baseline-only, and `evaluateMatches` keeps calling `ReadStateAt` when
`scopeID != nil`.

## Risk 2, aliasing: not a risk, and stepping is cheaper than assumed

`tony.Patch` does not mutate the document.  Checked directly: seed a document,
step it four times through field replace, add, delete and an `!arraydiff`
insert, and every intermediate tree is byte-identical to what it was when it was
made.

    h0 seeded  {a: {x: 1 y: 2} b: [1 2] c: keep}
    h0 now     {a: {x: 1 y: 2} b: [1 2] c: keep}   UNCHANGED
    h1 seeded  {a: {x: 10 y: 2} b: [1 2] c: keep}
    h1 now     {a: {x: 10 y: 2} b: [1 2] c: keep}   UNCHANGED
    h2 seeded  {a: {x: 10 y: 20} b: [1 2] c: keep}
    h2 now     {a: {x: 10 y: 20} b: [1 2] c: keep}   UNCHANGED
    h4 final   {a: {x: 10 y: 20} b: [1 2 3] c: changed}

It also shares structure: an untouched subtree is the *same pointer* in the
stepped result, not a copy.  So **a step costs O(patch), not O(document)** —
better than the plan assumed, and it means holding the head costs one document's
worth of nodes total rather than one per commit.

What survives of the risk is smaller and different: because subtrees are shared,
*mutating* a node reachable from the head would propagate into any tree sharing
it, including a watcher's `curDoc`.  So the rule is "nothing mutates the head",
not "nothing outlives the lock".  `evaluateMatches` navigates and calls
`tony.Match`, both read-only, so it is already within that rule.

## Risk 1, stepping from the wrong bytes: real, and already solved upstream

Raw `mergedPatch` is the wrong thing to step with.  `doCommit` runs
`TagPatchRoots` on it before merging, so it carries `!logd-patch-root` tags —
and those would end up on nodes in the head, where `tony.Match` would then see
them when evaluating a precondition.

The right form already exists, built on the same code path.
`newCommitNotification` (`storage/tick.go:177-182`):

```go
patch = mergedPatch.DeepCopy()
tx.StripPatchRootTagRecursive(patch)
```

and that is exactly what a baseline watcher steps with —
`tony.Patch(curDoc, notification.Patch)` at `session.go:913`, whose comment says
*"notification.Patch is already the tick's private, stripped copy, so it can be
applied as-is and is not mutated by Patch."*

So the head should step with **the notification's patch**, which
`WriteAndIndex` already constructs, under `commitMu`, on every commit
(`commit_ops.go:86`).  No new copy, no new cost, and the same bytes a baseline
watcher has been folding correctly all along.  Had this been stepped from raw
`mergedPatch`, the root tags would have leaked into precondition matching.

## A nuance the invariant has to survive

The invariant spans two different appliers:

- the read path applies the **stored, still-tagged** entry through the streaming
  processor — `patchNodesFromSegments` → `applyPatchesToBase` →
  `applier.ApplyPatches` (`storage/storage.go:274-302`);
- the head steps the **stripped** copy through `tony.Patch`.

They are supposed to agree, and that equivalence is not new to this work: the
baseline watchers already depend on it, and `read_equivalence_test.go:26` names
the fold-from-commit-0 via `tony.Patch` as *the semantics of record*, with the
snapshot path checked against it.

So the new test extends that oracle rather than inventing one, and it is testing
a property the system already relies on — which is the argument for stepping this
way rather than a reason to worry about it.

## Plan, revised

Unchanged in shape.  Three edits:

1. **Step with `notification.Patch`, not `mergedPatch`.**  Build the
   notification once in `WriteAndIndex` and use it for both the publish and the
   head step.
2. **Drop the clone-and-hand-out caution**; replace it with "nothing mutates the
   head", and note the structural sharing that makes the step cheap.
3. **Baseline only.**  `evaluateMatches` keeps `ReadStateAt` for
   `scopeID != nil`; scope is 9b2vpggxh12ks0qde5n0.

The drift guards stay as they were, and are worth more now that the invariant is
known to cross two appliers: nil-the-head on step error so the next read
re-seeds, and compare against a recompute at snapshot time, where the document
is being materialized anyway.
