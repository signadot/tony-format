Correction to my previous comment, and it removes an open decision rather than answering it.

I said the walkthrough's document shape was "something logd would have to store and hand back". Scott's point: logd is a separate binary over a wire protocol, so it cannot hold a consumer's operation in any case — the implementation is Go code in the client's process. There is nothing for a stored !ext:shout to mean, and asking whether the binding should be stored was the wrong question.

The client applies its own operations and sends the RESULT. That is already what the store keeps for a built-in relative operation: lowering applies !replace and stores what it produced, because an operation that re-evaluates later is one the store cannot answer for. A consumer's operation is the same case one step earlier — logd cannot apply it at all — so the client lowers it and what arrives is data.

So: contexts and namespaced operations are a LIBRARY concern, and the session protocol is unchanged. "What logd stores" is struck from the decisions; D2's choice about where a document's bindings live remains, and is now explicitly library-side.

What replaces it is a hazard rather than a decision, measured against the current build:

    patch a <- {greeting: !ext:shout "hi"}    -> accepted, no error
    read a                                    -> greeting: !ext:shout hi

To logd an unregistered tag is a DATA tag, not an operation, so a client that forgets to lower has its operation stored verbatim as decoration and is not told. Whether that write should be refused is its own decision and a hard one: the store cannot distinguish a consumer's operation from an ordinary data tag, which is precisely what !raw exists to make deliberate. Filed here rather than separately because it only arises once consumers have operations of their own.
