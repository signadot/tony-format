Correcting the comment above: the patch half of 7 is not a question, and the premise I gave
for it is wrong.

I wrote that "an op answers by handing something to f or pf, and both READ what they are
handed", and concluded a fetched object would merge. A patch op returns (*ir.Node, error).
It can answer with the value:

    func (kl embedOp) Patch(doc *ir.Node, ...) (*ir.Node, error) {
        toEmbed := kl.child.Clone()
        return kl.embed(doc, toEmbed)      // never calls pf
    }

!embed is the closest analogue and never calls pf at all. So !get-path installs with
`return V, nil`, "the value is what results" costs one line, and there is no merge to
choose against. The generalisation came from !let, which delegates to pf because its body
genuinely IS a patch, and !insert, which delegates because a merge is what !insert MEANS
-- `!insert {a: 1}` on `{b: 2}` gives `{b: 2, a: 1}`. Neither says anything about an op
which answers with a value.

What survives is the MATCH side, and only that side, because Match returns bool and has no
"answer with the value" option. It either hands V to f or compares structurally itself,
and handing V to f reads V as a PATTERN -- while V is data pulled out of a document.
Fetch something under a `!key(sku)` list and !key is read as an operator; fetch a value
whose tag is !glob and it globs. The meaning of a get would depend on the tags in the data
it fetched.

So: does the match side compare the document against the fetched value as DATA, or
interpret it as a pattern? !raw is the existing word for the first. One side, one
decision.
