Fixed in 7521f37. Your repro, run against the fix:

    FRESH STORE — nothing has ever been written:
      match the TRUE root (empty path)  -> Null
      match verse                       -> not_found: no value at "verse": no field "verse" at the document root
      match verse.a                     -> not_found: ...
      match verse.a.b.c                 -> not_found: ...

    AFTER writing verse.a.b.c = {x: 1}:
      match verse.a.b.c   (written)     -> Object
      match verse.a.b.ZZZ (absent)      -> not_found: resolved through "verse.a.b", no field "ZZZ"
      match verse.ZZZ     (absent)      -> not_found: resolved through "verse", no field "ZZZ"

    AFTER writing verse.n = null:
      match verse.n                     -> Null

The cause was one branch: extractPathValue returned ir.Null() for a nil document before it looked at the path at all. The error taxonomy already had the right kind waiting -- PathAbsent, whose own comment says a watch registered before the first write to its path reports this until someone writes there.

## One deliberate exception, for you to overrule if you want

The EMPTY path still answers Null on an empty store. A store where nothing has been written has a null root, and that seemed a fact about the store rather than about a path: no segment failed to resolve, so there is nothing to report absent. Every non-empty path reports absence. If you want the strict reading -- nobody wrote null at the root either, so the root is absent too -- say so; it is a two-line change, but it makes the first read a client ever makes an error, and I did not want to decide that for you.

## What it took beyond the one branch

Composition had been living off the old answer. A composed read fails if any source fails, and a source with nothing at its path used to contribute a null instead of an error -- so making logd honest broke TestDocd_ComposedWatchInitSucceedsStillStreams, a composed watch on a path nobody had written to yet, which is the normal way to start watching. That was a real regression, not a stale assertion. Absence is now carried as errSourceAbsent: a source reporting it contributes nothing, and the composed read reports absence only when EVERY source did, with the same not_found a direct read gives.

On the way there I found libctl's replyErr flattening everything but two cases to invalid_message, so a controller saying "nothing at this path" told the client it had asked wrongly. not_found now survives the trip.

One test changed meaning rather than spelling: TestDocd_ScopedComposedMatch wrote only in a scope and then read baseline, expecting an empty document. Baseline genuinely has nothing there, so it now reports absence. The test asserts the property instead -- a document coming back at all would be the scope leaking -- and still proves the isolation it was written for.

## Your two neighbours

Not addressed, deliberately.

An emptied container reading as {} is the same ambiguity one level up, but it is a different fix: the delete leaves the key in the parent, so the store genuinely holds an empty object there. Making that absent means deciding what a delete does to its key, which is a change to writes rather than to reads. Worth its own issue if you want it.

A null written at the root emptying the store is coherent under "a patch replaces", and it is now distinguishable from a fresh store in the way that matters: the fresh store's paths report not_found, and after the root write they still do -- but the root itself reads Null in both cases, which is the exception above.
