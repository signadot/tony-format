## 17. A struct-VALUE field of another package emits an import that is never qualified

Against **v0.0.92**.

A field whose type is an annotated struct in another package, held **by value**, generates a
package that does not compile: the import block names the package, but every use of the field
is a method call on the value, so the qualifier never appears.

```go
// spike/leaf/leaf.go
package leaf

//tony:schemagen=spike-leaf,notag
type Leaf struct {
	V string `tony:"field=v"`
}
```

```go
// spike/host/host.go
package host

import "github.com/signadot/verse/spike/leaf"

//tony:schemagen=spike-host,notag
type Host struct {
	Val leaf.Leaf `tony:"field=val"` // struct VALUE, and the only reference to the package
}
```

`tony-codegen -dir .` exits 0 and writes an import block containing

```go
"github.com/signadot/verse/spike/leaf"
```

while the only two uses of the field are unqualified:

```go
node, err = s.Val.ToTonyIR(opts...)             // ToTonyIR
if err := s.Val.FromTonyIR(fieldNode, opts...)  // FromTonyIR
```

```
spike/host/host_gen.go:12:2: "github.com/signadot/verse/spike/leaf" imported and not used
```

Note the generated *calls* are correct — resolution worked, the codec is reached, opts are
forwarded. The defect is confined to the import block: it is emitted for any resolved
cross-package field type, whether or not the generated body ever needs the qualifier.

**What masks it:** a *pointer* field of the same package. `FromTonyIR` allocates one
(`s.Ptr = &leaf.Leaf{}`), which qualifies the package and makes the import legitimate. So
adding `Ptr *leaf.Leaf` to `Host` above makes the package build again, and a type that has both
a value and a pointer field of the same package never shows the bug. That is why this took a
while to see: it needs a struct-value field to be the *sole* reference to its package.

**Why it matters:** same family as items 3 and 14 — a resolution/emission mismatch surfacing as
invalid Go rather than a diagnostic — but narrower and, unlike those, entirely mechanical to
fix. It also punishes the shape a wire type most naturally wants: a required nested struct is a
value, and making it a pointer only to satisfy codegen weakens the type (an absent nested
struct and a zero one become indistinguishable unless you *want* that distinction).

**Workaround in verse:** the field became a pointer. verse's new `api` package (named HTTP
request bodies, so the wire contract is one symbol shared by client and server) has

```go
//tony:schemagen=verse-set-vector,notag
type SetVector struct {
	Vector *process.Vector `tony:"field=vector"`
	By     string          `tony:"field=by,omitzero"`
}
```

where `Vector process.Vector` was the natural spelling. It happens to be defensible here —
`process.SetVector` takes a pointer, and absent-vs-zero is a real distinction for that request —
so the workaround cost nothing this time. It would not always be free.

**Suggested fix:** emit an import only when the generated body actually qualifies the package,
or (simpler and equivalent in effect) run the finished file through `imports.Process` /
`ast.Fprint` with unused imports pruned before writing.

### Item 5 no longer reproduces at v0.0.92

Unrelated to the above, but worth recording while it is in front of me: item 5 said generated
nested calls drop `opts...`. That appears fixed. In this repro, and across every generated file
in verse (48 nested calls in `api`, `launch`, `process`, `trigger`, `config`), the count of bare
`ToTonyIR()` calls is **zero** — all pass `opts...`:

```go
node, err = s.Val.ToTonyIR(opts...)      // cross-package, source-resolved type
node, err = s.Provider.ToTonyIR(opts...) // same-package pointer
```

I have not tested the shape item 5 was really about — a *hand-written* codec on a source-resolved
type reached from generated code — since verse still keeps those packages entirely hand-written
(item 4). So this is evidence for the common cases, not a claim that the root cause in
`methodAcceptsOpts` is gone. Worth a check before closing that item.
