My view on both, from the consumer side.

## 1. Name it — yes, unreservedly

Nothing to weigh. Today the message says WHAT went wrong (`let patching "null"`)
and not WHERE, so recovery is bisection by deletion, which is what I did to
staging under time pressure with reads down. Path plus commit turns that into
one lookup. If the compaction boundary is knowable too ("reachable from rev N"),
say that as well — the difference between "delete this entity" and "compact past
this commit" is the difference between losing a record and losing nothing.

## 2. Contain it — yes, with one condition that I would not bend

The blast radius today is the whole store, and for a consumer like verse that is
not one entity being unreadable, it is the ENGINE GOING BLIND: every trigger
evaluation reads the store, so one bad write stops every rule reasoning about
every subject. Containment is plainly better than that.

THE CONDITION: an unreadable path must never read as an ABSENT one.

That is not a style preference for us. verse is level-triggered — rules select
over the store and act on what they find — so a read that answers "nothing here"
for a poisoned path does not produce an error somewhere, it produces a WRONG
DECISION, silently and confidently:

  - a condition selecting `{state: open}` selects fewer subjects, and the rules
    that would have acted on them simply do not fire, forever, with nothing
    logged;
  - a `when` over a poisoned subtree evaluates false, so a gate that should hold
    a firing lets it through;
  - the engine's own guarantee that a firing reads ONE SNAPSHOT of the world
    becomes a guarantee about a world where those entities do not exist.

An outage is loud and gets fixed in minutes. A partial world is a charter acting
on a false premise for as long as nobody notices. We already hold this line
elsewhere for exactly this reason: a missing `!get-path` target FAILS the firing
rather than resolving to nothing, so that "nothing is there" cannot launder into
"something is there, and it is nothing".

So, concretely, what I would want:

  - `Get(P)` on a poisoned path: an ERROR naming P. Never a not-found.
  - anything that SPANS paths (list, select, watch, snapshot): either it errors
    as a whole, or it returns results together with the set of paths it could
    not read — named, in the reply, so the caller can decide. verse would decline
    to fire on a partial selection rather than act on it.

If carrying "partial, and these failed" through the list APIs is too big a
change, then erroring the whole list is the right fallback and still an
improvement, because `Get` of unrelated paths keeps working and the store stays
diagnosable.

## 3. The one that would have saved us: refuse the WRITE

Both of the above are about surviving a poisoned store. Better is not accepting
the poison. verse already refuses these on the way in — `CheckPatchable` rejects
`!let`, `!glob`, `!irtype` in a bare payload — and deliberately passes them under
`!raw`, because `!raw` is the contract that says the subtree is data. The store
is the only party that knows whether it can actually honour that for a given
operator. If it cannot, the WRITE should fail: attributable to the writer, at the
moment they did it, costing nobody else a read.

Ranking, if it matters: (3) prevents the class, (1) makes the survivors
recoverable, (2) bounds the damage. (1) is free. I would take (2) only with the
absent-vs-unreadable line held.
