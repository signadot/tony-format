CORRECTION — my docd/logd framing was wrong, and I am sorry for the detour. docd is not involved. The post-snapshot hypothesis is right, and here is a deterministic recipe with no docd and no verse server in it.

RECIPE. Against a bare in-process logd (maxCommits 1000), write 995 ordinary entities, then twelve entities whose id contains a dot, one per commit:

    rev=996   dot.ted0   landed=true
    rev=997   dot.ted1   landed=true
    rev=998   dot.ted2   landed=true
    rev=999   dot.ted3   landed=true
    INFO triggering snapshot commitsSinceSnapshot=1000
    INFO snapshot created commit=1000 logFile=A position=439505
    rev=1000  dot.ted4   landed=true
    rev=1001  dot.ted5   landed=FALSE
    rev=1002  dot.ted6   landed=FALSE
    …every one after it FALSE

'landed' is: Patch at `verse.zz.probe."dot.ted5"`, then Match at the same path. The write commits and reports a revision; the read finds nothing, and the value is at `verse.zz.probe.dot` → `ted5` instead — the quotes are gone and the segment has split on its dot. The commit that TRIGGERS the snapshot (1000) is still fine; everything from 1001 on is not.

Bisected: 999 filler writes then a dotted one → lands. 1000 then a dotted one → does not.

WHY IT LOOKED LIKE docd, and the trap to avoid when testing this. Two false negatives cost me most of a day, and both will bite anyone verifying a fix:

1. A fresh store never reaches 1000 commits, so any small test passes. My 'plain logd works, docd fails' A/B was really 'a 3-commit store works, a 2000-commit store fails'. Both faces fail once past the snapshot; I have since reproduced it on a bare logd with no docd anywhere.

2. A PRIOR WRITE AT THE SAME ADDRESS MASKS IT. Write the dotted id before the snapshot, cross it, write the same id again: the read answers ok=true and returns the OLD payload, because the second write went to the split address and the first entity is still standing. My probe reused one id across runs and looked clean for exactly this reason.

So a test for the fix wants a distinct id per probe and >1000 commits ahead of it.

VERSE-SIDE CONSEQUENCES stand as reported: a put answers 204 and stores nothing at the address named, and a delete misses the same way, which is what left 192 of 721 entities standing after `verse source remove --forget` — every one of them a ref with a dot in its id.
