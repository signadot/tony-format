Root cause found, and my characterization here was WRONG. This is not presentation-specific and not benign: it is a symptom of 1xnezrpkh12ksavvjdn0, where a narrow read silently returns STALE DATA when a write's patch root sits above the read path.

Why it looked like presentation. A lowered no-op !rename stores

    {a: !addtag(bracket) null}

and markDeltaRoots marks that at the document ROOT, because it cannot descend past a null value -- the descent requires the single field's value to be an object. A read at "a" is therefore BELOW the marker, patchAtPath descends past it, the projected node is unmarked, and the streaming processor drops the entry. What that entry happened to carry was a tag, so the loss showed up as style.

The same store shape with a value under the path loses the value:

    write  a  <- {k1: 2}      [snapshot]
    write  "" <- {a: {k1: 77}, other: 1}
    read   a  ->  wide {k1: 77}, narrow {k1: 2}

Confirmed on main as well as on worktree-lowering, with no scope and no lowering needed -- LowerEverything only makes the presentation variant easy to generate.

Correction to what I wrote above: "presentation only; not scope-specific" was right about scope and wrong about presentation. The 4 restyled counts in TestNarrowScopedReadMatchesTheWideRead are all this bug; that generator never produces an ancestor-marked write that states a value under a path it also reads, which is why it only ever surfaced as style there.

Keeping this open as the presentation-shaped instance, but it should close with 1xnezrpkh12ksavvjdn0 -- there is one defect. The 'restyled' counter and its comment in read_subtree_scope_test.go should be re-pointed at that issue when it is fixed, and the differential's generator wants a write whose marker is strictly above a path it reads.
