## Plan

This would go on branch `issue-x32pp5j0h`, from main, in two commits: fix 1 alone, then fixes 2 and 3 together, because 3 comes out of the goroutine 2 introduces. The ping stays on the loop. `maxConcurrentReads` stays at 8, and it becomes the single bound on the memory held by reads in flight, opening pictures included.

### Fix 1: a match takes its slot off the loop (`session.go` dispatch)

- `readWG.Add(1)`, then start the goroutine. It acquires the slot inside, with `select { case s.readSlots <- struct{}{}: case <-s.done: return }`, and releases it when `handleMatch` returns. The loop goes straight on to the next request.
- Ordering is unchanged. Reads already run concurrently and are answered by id, out of order. A read dispatched after a write still starts after that write committed, so it reads at or after that commit, and read-your-writes holds.
- Shutdown is unchanged. A waiting goroutine leaves on `done`, and `readWG.Wait()` covers it.
- Update the comments at `session.go:54`, `:263` and on `dispatch`. They currently say the loop waits past the 8.
- **No cap on queued reads.** The 8 bounds memory held by reads, and a waiting goroutine holds only its parsed request. If a cap is wanted, a request past it would either block the loop, which brings this stall back, or be refused with a new busy code that libctl has to handle. Not proposed.

### Fixes 2 and 3: a watch open reads off the loop, once, inside a slot (`session_watch.go`)

**Stays on the loop, as today:**
- admission
- `hub.Watch`
- `GetCurrentCommit`
- the respelling check
- the past-the-head refusal
- the `watches` entry
- the relative and answered-commit cursor adjustments
- the replay range

These fix where the watch sits against requests sent after it. `currentCommit` is still taken before any later patch commits.

**Moves into one goroutine, tracked by `readWG`, in this order:**
1. Take a read slot, with `select` on `done`.
2. If the watch has dropped out of `s.watches` while it waited (see the unwatch case below), stop.
3. Read the path at `currentCommit` once. Skip this when nothing needs it: `waitIfAbsent` together with `noInit`, or a `fromCommit` with `waitIfAbsent`. `commit == 0` keeps its no-read answer.
4. If the read finds the path absent and the watch is not `waitIfAbsent`, apply today's refusal: `hub.Unwatch`, delete from `watches`, then `ErrCodeNotFound`. It still comes before the confirmation.
5. Send the confirmation.
6. Run `forwardEvents`, which:
   - refuses a cursor below the floor, as now
   - sends the opening picture, reusing the value from step 3 when `startCommit == currentCommit` and reading at `startCommit` otherwise
   - then releases the slot, and only then runs the replay and goes live

`sendInitialState` would take the read it is given as a `(node, err)` pair, so the PathError classification at `:399-422` applies to a reused read exactly as it does now.

**Effects:**
- Each open reads its path once instead of twice.
- No more than 8 matches and opening pictures run at once per session.
- Opens queue as goroutines, not on the loop.

**Cases to settle in review:**
- **Unwatched while queued.** `handleUnwatch` runs on the loop. It removes the watch, unregisters it and answers. The queued goroutine sees the watch gone, but the watch request still needs an answer, exactly once. My proposal is `ErrCodeNotWatching`, saying it was unwatched before it was established. That needs checking against docd's `releaseIfEnded` (`docd/server/client_session.go:669`), which releases a watch's reader token on a refusal, because the unwatch has already released it.
- **Progress before confirmation.** A progress request for a watch that is still queued is acknowledged on the loop, ahead of the confirmation. Its event still follows the opening picture. No change.
- **A long wait in the queue.** The watcher is registered with its 1,024-event buffer before it waits. If more than 1,024 notifications reach its path meanwhile, it fails as a slow consumer, the same rule as for a stall today.

### Not covered: the write side

The pong is queued on `outgoing` (buffer 100) behind frames that are already queued, and docd writes its own pong on the client connection behind the logd pump. After these fixes, at most 8 opening pictures are being built at once, plus 100 frames buffered. Large pictures on a slow link could still push a pong past 5s. Fixing that would mean a priority lane for pongs in the writer. It would be a separate issue, if wanted.
