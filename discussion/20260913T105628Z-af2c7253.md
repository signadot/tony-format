item 18: NOT fixed, analysis only. Root cause is parse-time comment association, not the encoder. For `[\n  [\n    1\n  ] # c\n]`, the tokens are correct (TLineComment ' # c' on the same line as the inner ']', L3), but the parser attributes that closing-line comment to the ENCLOSING array, not the inner element: after Parse, outer.Comment.Lines=['  # c'] and inner.Comment=nil (verified by instrumenting parse). The encoder then renders the top array's line comment on its own trailing line ' # c' after the outer ']', which reparses as 'imbalanced document: trailing material'. This is the hard comment-association class the parser already handles with a dedicated correction pass (associateComments, see the p==nil block in parseBalanced and its comment). A correct fix belongs there -- attribute a comment on a multi-line bracketed value's closing-bracket line to that value -- and must be validated against the whole comment test suite (token, parse, encode, stream roundtrip, match/patch comment tests); it is materially larger and riskier than items 15/16, so it is left for a focused change rather than half-fixed here. docs/tony.md's Comments section does not state where a comment on a closing bracket line associates; that rule should be added with the fix.
