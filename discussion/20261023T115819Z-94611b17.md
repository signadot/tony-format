Confirmed from the tony-format side, on the same docd-0 (admin face port-forwarded, 2026-10-23 ~11:55 UTC, a compaction in flight). A 30s CPU profile: `leafRange` 17% flat / 40% cum, `parentRange` 54% cum, `sort.Find` 9%, `segmentsWithin`/`touched`/`missing`/`commitsUpTo` beside them; decoding ~3%; GC ~15%. Index fully resident (`index.ceiling: 0`, 382 MB resident, 0 evictions), so this is CPU on the walk, not paging. `reads.narrow.avg` 187ms, `writes.avg.apply` 280ms, `writes.slow` 71k of 139k commits.

**Why the walk sees everything, in the code.** `segmentsWithin` ranges the node's `Commits` tree with `commitsUpTo(to)` as the bound, and that comparator only ever answers 0 or 1: it stops the walk past `to` and never skips below `from`. The tree can skip below (`parentRange` skips a child whose `max()` compares < 0), but the key is `StartCommit` and a segment may start before `from` and end inside it, so a lower bound on the key is unsound. That is the hole the comment on `commitsUpTo` describes (tmwq9mh6h12kskmxj9n0), and the fix shape it leaves open: give each tree node the **max EndCommit of its subtree** (the interval-tree augmentation, kept on add/remove/split/merge as `min`/`max` are), and let the comparator answer -1 when that max is below `from`. Then a read from a snapshot at S walks only subtrees holding a segment ending at or after S, at every ancestor: bounded by the writes since the snapshot, which is what `Segments`'s comment promises. Spine segments at ancestors stop mattering because they are filtered out of the small set that is visited, not the whole history. On this store that turns ~66k visits per ancestor into ~1k.

**The compaction side**, same host: the compaction goroutine was in `writeCompactedEntries` → `ReadEntryAt` → `decodeEntry` → `EventsToNode`: it decodes every surviving entry to a full IR node to read `entry.SnapPos`. `compactionRecords` decodes them all once before, and `reindexEntry` decodes each survivor again after the swap: three full decodes of ~60k entries (~645 MB) per cycle, on the two cores the reads hold. The rewrite copies ~640 MB to drop ~3–5k of ~64k entries. And each cycle takes ~25 min while the snapshot trigger fires the moment it ends (1,000+ commits accrued meanwhile), so the store compacts back to back, all day: 10:02→10:27, 10:27→10:53, 10:53→11:18, 11:18→11:39, 11:54→…. Meanwhile `snapshotPath` takes `snapMu`, which the compaction holds, so path snapshots are off for the duration: `snapshots.path.no.busy` 433,961, and reads fold tails up to 2,722 records. Filed apart: the decode-three-times and back-to-back scheduling, and the path snapshots blocked for the whole compaction.
