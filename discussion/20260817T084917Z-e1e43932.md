Both halves fixed in a6779b2, and the answer to "can !all.irtype t work?" is no.

## The element check

`t` arrives bound to a definition BODY -- `env["int"]` is a whole match -- and a
match has no spelling as a tag component, so `argToTagString` returned "" and the
tag became `!all.`. SplitChild folds a component naming no operation into the node
as data, so the clause was `null` with decoration on it, and a null payload matches
everything. `!all.irtype t` does not fix that: the argument is still a body, and
even spelled with a plain name the SAT check rejects the definition, because
`!and [.[array], !all.irtype t]` puts the element constraint at the CONTAINER's
position -- array AND string, UNSAT, reported as `definition "arr(t)" has
impossible cycle`.

The parameter goes in the value position, where the body substitutes whole and the
tag it wore composes over the tag the body has:

    array(t): !and
    - .[array]
    - !all t

Dropping the composed tag was a second bug in InstantiateDef: `!all t` with t
bound to a tagged body lost the `!all` and matched the container against the
element type. Same shape retagRef fixes for `.[ref]`. A parameter named in a tag is
now an error naming it; BuildDefEnv's closures propagate it instead of returning
nil, which expansion turned into null, which matches everything.

object(t) named a parameter and used it nowhere at all. nullable(t)'s `!t null`
made it accept anything. Both fixed the same way.

## `.[int]`

Not "the IR encoding" -- nothing at all. `!and [.[number], {int: !not null}]` asks
for a node which is both a Number and an object, and both halves are independently
broken: an object pattern is about the DOCUMENT (match.go refuses it unless the
document is an object, then reads the document's children), and `!not null` matches
nothing, since a bare null matches everything. So `age: .[int]` rejected `age: 3`,
and tony-codegen emits `.[int]` for every Go int.

Re-nesting the two clauses cannot fix it, because neither can observe integralness:
that lives in Node.Int64, and the only place the match language reads it is a bare
numeric literal, which welds kind to value. New operator, `!ir`, which matches a
pattern against the node's own IR fields:

    3         !ir {type: Number, int: 3}
    3.5       !ir {type: Number, float: 3.5}
    !k v      !ir {type: String, tag: "!k", string: "v"}
    {a: 1}    !ir {type: Object, fields: [a], values: [1]}

    int: !ir {int: .[number]}
    float: !ir {float: .[number]}

A field the node does not have is absent, so saying what a field HOLDS is
insensitive to which fields are pointers -- Bool is not one, and `!ir {bool: null}`
does not match false, which is why bool stays `!irtype true`. fields and values
hold the document's own children, so a pattern under them descends and !ir applies
again wherever written.

_ir keeps no !ir: with one it would describe every node, and `.[ir]` -- whose job
is to say a document IS an IR encoding -- would accept everything. _ir describes
that document; !ir asks a node about itself.

## Guards, so this class cannot ship again

The satisfiability checker passed base.tony's own int, and each reason is now
closed: a bare null builds to T (so `!not null` is empty), an object pattern
asserts objecthood at its position and an untagged array arrayhood, and !ir builds
to an opaque literal so its negation stays satisfiable. It now rejects
`!and [.[number], {int: X}]`, `{age: !not null}` and the old int verbatim.

Cost, worth knowing: twelve documented examples used `!not null` for "required and
non-null" and are now rejected at parse rather than silently accepting nothing.
Rewritten as `!not.irtype null`. A schema in the wild written from those docs gets
a hard error where it used to get a vacuous pass.

## Evidence

    $ o schema check s.tony mixed.tony      # accept: .[array(int)]

    $ o schema check i.tony nums.tony       # - 1 / - 2
    ok                                                        exit 0
    $ o schema check sage.tony agef.tony    # {age: .[int]} vs age: 3.5
    age: ir: expected !ir {int: !irtype 1}, found 3.5         exit 1

## Still open here

sparsearray accepts nothing: its key clause `!all.field.type 0` asks each key to
be a number, and !field hands over the key's NAME as a string (mergeop/field.go),
which is never a number. Being fixed next.

Two more found on the way, not yet filed:

  - Definition lookup is indexed by base name, so `foo` and `foo(t)` collapse to
    whichever the map iteration keeps (formula_builder.go's defIndex,
    findReachableDefinitions). Which of the two gets its satisfiability checked is
    therefore nondeterministic -- it flaked a test of mine.
  - A legitimate recursive definition stack-overflows instead of erring:
    `node: !or [!irtype null, {next: .[node]}]` passes the cycle check as
    satisfiable, then ExpandDefBody expands eagerly and dies. It is why _ir and ir
    have to be skipped when base definitions are merged.
