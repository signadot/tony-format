-m Not scope-specific after all, and reachable from baseline in three writes. The condition is
that the BASE holds the array -- a snapshot -- and a later entry writes a field beneath it:

    baseline  ""     <- {k2: [{n: 1}], other: 1}
    SwitchDLog
    baseline  k2.n   <- 5                       (accepted; verification reads k2.n, which is absent)
    read k2.n  = 5
    read other = 1
    read k2    : failed to apply patches: cannot graft [n] into the array at "": creating array elements needs the key field
    read ""    : failed to apply patches: cannot graft [n] into the array at "k2": ...

So the store accepts a write and then cannot read the path it landed under, or the root,
until something replaces k2 whole. Without the snapshot the same three writes read fine,
because the array is then a patch in the fold with a root at k2, k2.n is dominated by it,
and the object write is applied at k2 through tony.Patch, which replaces the array.

verse does not reach it: descendsThrough refuses a write that descends through anything but
an object, a null or nothing. Any other client can. It is the class of defect CheckPatchable
was written for -- a write the store accepts and then chokes on -- on the store's own side.

Where it sits: unreachedPatches.graftUpTo fires at a container's CLOSE, after the array's
elements have already streamed, so replacing there is too late; the fix on the fold side is
to decide at the array's OPEN, when pending field paths beneath it are already known, that
the array is replaced -- its events dropped, an object of the grafted fields emitted in its
place -- which is what tony.Patch answers for the same pair. The fix on the write side is to
refuse at verification, which needs the site's parent read, not only the site.
