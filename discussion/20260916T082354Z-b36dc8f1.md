Flow control: a limit, and therefore a cursor.

A caller that asks for a set of unknown size has no way to stop it -- there is no unmatch, and the sequence is already in flight. A limit on the request bounds it, but a limit alone leaves the caller with a truncated set and no way to ask for the rest, so the pair is limit plus cursor: this is a pagination interface, and it belongs to the protocol rather than to match.

Shape:

- the request takes `limit` (the most members in one page) and `cursor` (continue a paging read);
- the terminal marker carries `cursor` when more remains, and omits it when the set is finished. The marker is the authority: a page shorter than `limit` does NOT mean the set ended, since the server may cap a page below what was asked. That is the same choice replayComplete already makes -- say it, rather than have the client infer it;
- within a page, members still arrive one at a time. Pagination bounds the request; streaming is how a page is delivered. The two are not alternatives.

Why a cursor is cheap here: the store is versioned, so a cursor needs no server-side iterator and no session affinity. It is (the commit the set was read at, the last path answered). Continuing is a read at that same commit, resuming after that path -- so every page of a paging read is one snapshot, and a page boundary never straddles two states. A continuation whose commit has fallen out of range answers commit_not_found, as a historical read already does, rather than silently reading current.

That requires the walk to have a total, stable order, which it has: object keys are sorted on write and on read, so the order is the walk order over sorted levels, and a resume seeks to the cursor position per level rather than rescanning what it already answered.

The cursor is opaque to the client. That is what lets docd compose one: a composed cursor is a bundle of per-participant cursors, and a client that parsed it would be parsing a shape docd is entitled to change (see 5f6vrzw0h12ksrtfn9n0).

Since this is a protocol interface and not a match feature, it should be defined once and reused by every operation that answers a set: the wildcard match here, an any-depth read later (th7sdhvyh12ksjtfn9n0), docd composing across mounts, and anything else that grows a set-shaped answer.
