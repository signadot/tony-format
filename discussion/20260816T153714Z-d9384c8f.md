Fixed, in go-tony/v0.0.148, by two commits which say the same thing at two altitudes.

0ac684d: a write at an array index must name an element, checked when it is SUBMITTED -- where
the array's length is a fact the client can be told, and off the commit lock -- and again at
commit, where the head makes it cheap and where it is the last moment before the delta is
stored. patch and delete need i < len; insert needs i <= len; an index that is not the last
segment always needs i < len, since a write cannot insert THROUGH a position on its way deeper.
The refusal is invalid_path with the array's length in it, where it used to be a storage_error
or, in a transaction, tx_full.

8e1b334: the general statement this issue is one instance of. Every patch is applied to current
state before it is stored. The apply was already happening -- stepHead did it one step later,
after the entry was written, where its only possible answer was to drop the head -- so moving it
ahead of the write and making its failure the write's failure costs baseline nothing.

The framing in the "Where the check belongs" section above was right and the reason under it
was incomplete: it is not that an index is special, it is that a delta which does not apply must
not be stored, and an index past the end is one way to write one. A !replace whose from: is not
what is there is another, and was equally fatal.

Two things this issue touched are open on their own:

  c2r55zf2h12kr1y4g5n0  the write is checked for EXISTENCE, not identity, so a concurrent
                        insert or delete before the index retargets it silently
  7ftjmf1ah12kranxg5n0  !insert at [0] of an array which does not exist is refused for now,
                        because arraydiff cannot create one

The verse-side test named at the bottom of this issue (entity/arraywrite_test.go) pins the old
behaviour and should now hear about it: logd refuses the write rather than accepting it.
